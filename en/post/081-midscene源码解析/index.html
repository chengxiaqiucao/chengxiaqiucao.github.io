Source Code Analysis of the AI Automation Tool Midscene.js

Jun 22, 2025
18 minute read
中文

Preface

In a previous article 【】we learned about the AI testing tool Midscene.js launched by ByteDance. Whether it is intelligent project parsing, test execution, or the final report generation, it is quite impressive; moreover, in addition to browser-based web applications, it also supports the automation of Android apps.

So how exactly does this project use AI intelligence to complete test execution tasks? In this article, we will draw on the open-source project source code of Midscene.js to conduct an in-depth analysis of the project’s implementation as well as its application of large models.

Overall Project Architecture

Through the analysis of the project source code, the overall architecture of the project can be summarized by the following diagram:

  • User: The user is the starting point of Midscene, defining automation tasks and goals through natural language descriptions, the JavaScript SDK, or YAML scripts.

  • MCP Clients: Midscene also supports other MCP clients directly using its capabilities, which indicates that it may have an API or integration point for other systems to call.

  • Midscene Core: This is the core logic layer of Midscene. It is responsible for parsing user instructions, interacting with AI models, and coordinating automation agents to perform operations. It also manages report generation and caching.

  • AI Models: Midscene supports multiple AI models, including:

    • Multimodal LLM: such as GPT-4o and Gemini-2.5-Pro, used to understand more complex instructions and context.

    • Visual-Language Models: such as Qwen2.5-VL, Doubao-1.5-thinking-vision-pro, and UI-TARS, which are especially recommended for UI automation because they can better understand visual information. The AI model receives requests from Midscene Core and returns instructions to execute actions or retrieve information.

  • Automation Agent: This is a key execution layer, responsible for actually operating the target application or UI according to the instructions of Midscene Core. It can obtain the UI state and screenshots and feed them back to Midscene Core.

  • Target Application/UI: This is the actual object of automation operations, which can be:

    • Browser: Web automation through tools such as Playwright or Puppeteer.
    • Android App: Performing Android automation.

  • Visual Reports: Midscene provides visual reports to help users understand, replay, and debug the entire automation process.

  • Playground: The built-in Playground environment allows users to debug through natural language instructions.

  • Caching Mechanism: Midscene uses a caching mechanism to improve efficiency, allowing scripts to replay more quickly to obtain results.

Large Model Context Window Limitations

When using various AI large models to complete intelligent tasks, a very important constraint is that large models usually have a context window size limit; historical information exceeding this limit is discarded in order to conserve the resources of the large model and improve performance.

For an automated testing task, however, the execution chain after decomposition is often long and usually exceeds the LLM’s context limit.

So here we further analyze how this project handles the context window limit.

1. Token Count Limit Control

The project sets the maximum number of tokens in the response through the OPENAI_MAX_TOKENS environment variable

2. Image Size Limits and Automatic Adjustment

The project implements image size limits for different models, especially strict size control for the GPT-4o model. When it detects that the image size exceeds the maximum input limit of GPT-4o (2000x768 or 768x2000 pixels), the system issues a warning.

let warned = false;
export function warnGPT4oSizeLimit(size: Size) {
  if (warned) return;
  if (getModelName()?.toLowerCase().includes('gpt-4o')) {
    const warningMsg = `GPT-4o has a maximum image input size of 2000x768 or 768x2000, but got ${size.width}x${size.height}. Please set your page to a smaller resolution. Otherwise, the result may be inaccurate.`;

    if (
      Math.max(size.width, size.height) > 2000 ||
      Math.min(size.width, size.height) > 768
    ) {
      console.warn(warningMsg);
      warned = true;
    }
  } else if (size.width > 1800 || size.height > 1800) {
    console.warn(
      `The image size seems too large (${size.width}x${size.height}). It may lead to more token usage, slower response, and inaccurate result.`,
    );
    warned = true;
  }
}

3. Image Compression and Optimization

The system reduces the amount of data transferred through image compression (packages/shared/src/img/transform.ts), including:

  • Setting the image quality to 90% to balance quality and file size
  • Providing image resizing functionality
  • Supporting image processing and conversion in base64 format

4. Choosing the Right Model Architecture

The project supports two different types of AI models to optimize token usage:

General-purpose multimodal LLM (such as GPT-4o): Requires sending both the screenshot and the DOM tree, resulting in higher token consumption.

Visual grounding VL model (such as Qwen-2.5-VL): Supports visual grounding and does not need to send the DOM tree, saving 30% to 50% of tokens.

See the explanation in the apps/site/docs/zh/choose-a-model.mdx document

5. Token Usage Monitoring

The project also provides detailed token usage tracking and debugging features, recording prompt tokens, completion tokens, and the total number of tokens.

In summary, the project’s strategy for handling context window limits mainly focuses on three aspects:

  • Controlling the input data volume (through image compression and size limits)
  • Choosing the right model architecture (VL model vs. general-purpose LLM)
  • Monitoring and optimizing token usage

This multi-layered approach effectively reduces the need for large context windows while also maintaining functional completeness.

Memory Management for Long-Chain Tasks

For large models, the memory of completed steps and historical tasks is of great significance for ensuring result accuracy, avoiding unnecessary repetition, and saving costs. As introduced in our previous articles, tools such as Browser-Use bring in memory frameworks like mem0 to implement AI memory capabilities; so how does Midscene handle this aspect?

Based on the analysis of the Midscene code, memory management for long-chain tasks is mainly implemented through the following core mechanisms:

Task Caching Mechanism

Midscene implements an intelligent task caching system to manage the memory of AI operations. This system caches planning results and element location information to avoid repeated AI calls, thereby reducing memory consumption and improving execution efficiency.

packages/web-integration/src/common/task-cache.ts

The caching system supports two types of cache:

  • Planning Cache (PlanningCache) is used to store the AI-planned YAML workflows
  • Locate Cache (LocateCache) is used to store the XPath information of elements.

Conversation History Management

To prevent the conversation history in long-chain tasks from growing indefinitely and causing memory overflow, Midscene implements an intelligent conversation history management strategy. The system limits user image messages to a maximum of 4 retained entries and adopts a first-in-first-out (FIFO) strategy to automatically clean up old conversation records.

packages/web-integration/src/common/tasks.ts

Replanning Limit Mechanism

To prevent the AI from falling into an infinite replanning loop in long-chain tasks, the system sets a limit on the number of replanning attempts. When the number of replanning attempts exceeds the limit, the task proactively terminates and returns an error message.

Context Optimization

To reduce memory usage, Midscene also implements several context optimization strategies:

  • Visible element filtering: Only extract the visible elements on the page, reducing the size of the DOM tree
  • Image compression: Intelligently compress screenshots to reduce memory and transmission overhead
  • Viewport cropping: Crop context data according to the viewport range

It can be seen that although Mdscene has not introduced a dedicated memory framework to handle historical memory, it has nevertheless established a memory management mechanism to handle this collaboratively, enabling Midscene to maintain efficient memory usage when processing complex long-chain tasks. Through conversation history management to control memory growth, replanning limits to prevent infinite loops, and resource cleanup to ensure system stability, it ultimately achieves a reliable long-chain task execution system.

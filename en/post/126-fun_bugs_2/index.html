A Fun Bug Story - The Norway Problem

Sep 13, 2025
4 minute read
中文

In the previous series, we shared the origin of Bug, some close relatives similar to Bug, and also an interesting classic Bug. In this article we share another very typical Bug, one that the author has personally encountered.

A Strange Page Crash

The author once tested a web application related to import and export trade. One page displayed information about trading partners, similar to the figure below.

There was an auxiliary feature that could export transaction information as a standard-format document meeting the requirements of the counterparty’s country (of course, the format is actually the same for most countries).

This feature showed no problems during testing.

But after delivery to users, at one particular customer, once this export operation was triggered, the page would intermittently crash - a serious problem.

Locating the Problem

After receiving this feedback several times, it was found that whenever this user experienced the crash, without exception, the counterparty’s trading country was Norway, and the document exported for that country was also a standard document. So it was not a problem with the exported document format.

After analyzing the implementation logic of this feature, the crux of the problem was finally found.

In this export feature, the matching of document formats is defined in a YAML configuration file, and country identification is configured in YAML via country codes. And Norway’s country code is NO

Something like:

1
2
3
4

config:
 - filetype: pdf
 - profile: standard
 - country: NO

According to the definition in the YAML V1.1 standard specification (https://yaml.org/type/bool.html):

After the code interprets NO, it is treated as the boolean value False. And the program here lacks configuration validation and exception protection, causing an exception when reading the country code and resulting in a page crash.

So the causes can be summarized as:

  1. YAML configuration file: the country code configuration is treated as a string by default, without considering special cases like NO, and no string quotes were added.
  2. Program handling: lacks validation of the correctness of YAML configuration values.
  3. Insufficient exception protection: an exception directly causes the page to crash.

Fixing the Problem

Once the cause is found, the fix is actually very simple: for the country code, force-convert it to a string before processing, and add validity checks and exception protection code. Of course, for YAML configurations that easily cause ambiguity, string quotes were also added.

1
2
3
4

config:
 - filetype: pdf
 - profile: standard
 - country: "NO"

Reflection

Actually it is not just country codes. In string-type fields, using other characters with special meanings, such as “Yes”, “null”, etc., can also cause similar problems.

Therefore, for us in testing, data handling verification during testing, especially the handling of similar special characters, must take relevant scenarios into account; otherwise it is easy to miss similar serious problems.

A Fun Bug Story - The 500-Mile Email

Let’s continue sharing classic Bugs from history.

This Bug is also quite bizarre:

The story takes place in 2002. That day, the head of the statistics department at MIT approached Trey Harris, the person in charge of the campus email system, complaining about a rather bizarre problem: “Our emails can’t reach anywhere beyond 500 miles. Actually, 520 miles is more accurate.” The admin’s inner voice: ^&^(&………&))(&^% But no matter how hard he disbelieved it, he still tested it himself with his own mailbox. The result was actually true! Just as reported, emails could only be sent within 520 miles, and any email beyond that range failed to send.

After some investigation, the cause was finally figured out.

It turned out that not long before, the operating system of the mail server had just been upgraded (still SunOS back then), and OS distributions at that time usually came bundled with some accessory software, but the versions of these pieces of software were often quite old (just like updating Linux, the bundled Python version is usually not the latest). So after the system update, the version of the mail software they used, SendMail, was downgraded (SendMail 8 -> SendMail 5).

And updating the system also kept SendMail’s configuration file sendmail.cfg, so the following situation arose: SendMail 5 would parse SendMail 8’s configuration file.

Because sendmail.cfg contained a configuration item timeout to connect to the remote SMTP server that SendMail 5 did not support, that is, the timeout for connecting to the remote SMTP server. For this unsupported configuration, SendMail 5 simply ignored it and treated it as the default value 0. And later experiments showed that a timeout of 0 seconds would cause Sendmail to interrupt the connection after 3 milliseconds.

So why 500 miles?

Back then, there were not many routers in MIT’s campus network, so network latency was very low - that is, the time to connect to a remote host was roughly close to the speed of light. So 3 milliseconds meant:

0.003 * 3 * 10 ^ 8 * 0.001 * 0.621 = 558.9

Considering the low network latency, this is how the 500-mile problem came about.

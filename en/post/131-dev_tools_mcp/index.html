Chrome Launches DevTools MCP, Adding a New Option for Browser-Based AI Automation

Oct 16, 2025
8 minute read
中文

In previous articles, we introduced various browser AI automation tools such as Playwright-mcp, browser-use, and midsceneJs; each can well drive a browser to complete automated tasks based on AI large models.

Recently, Google officially launched the devtools mcp for the Chrome browser, further enriching the tools for driving a browser to complete intelligent tasks through AI, including executing automated test scripts.

What Is DevTools MCP?

In short, DevTools MCP is Google exposing the underlying devtools methods of the Chrome browser, based on the MCP (Model Context Protocol) standard, to AI large language models (LLMs) as a service, enabling AI large models to call the underlying debugging tools of the Chrome browser.

For a detailed introduction to MCP, see my previous article 【】

Chrome DevTools MCP Architecture

The tool uses a layered architecture, mainly including the following modules:

  • MCP Server layer: Responsible for receiving MCP requests from the LLM/agent, and performing session management and permission control.
  • Tool adaptation layer: Maps MCP’s high-level requests to the Chrome DevTools Protocol (CDP) or Puppeteer API, and manages long tasks (such as recording/tracing).
  • Chrome runtime: A real Chrome/Chromium instance (headful or headless) that performs all underlying operations and produces trace, performance, console, and other data.
  • Data collection and transmission: Serializes the collected trace, stack, HAR, snapshots, and other data, and returns it to the caller via MCP.

Installation and Usage

The tool is open-sourced on GitHub at:

https://github.com/ChromeDevTools/chrome-devtools-mcp

Compared with other tools, configuration and installation are extremely simple, and the homepage also provides quick configuration for various mainstream AI terminals.

Taking Cursor as an example, in its MCP configuration page, add the following configuration:

{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",

}

Just make sure Node.js is installed locally and can connect to the node package management server.

Compared with other upper-layer tools like Playwright-mcp, Chrome DevTools, calling directly from the browser’s lower layer, should be faster and more accurate in execution, and should also be friendlier in token consumption when interacting with large models.

### Assessment Target

- Site: https://chengxiaqiucao.github.io/ (Hugo + Stack theme)

- Reference source: The site's public content and this sampling result

- Homepage content reference: Qiucao's Testing Observation

### Key Metrics (Lab)

- Desktop environment (no throttling/no slowdown)

- LCP: 477 ms (largest contentful paint is the homepage hero image, IMG)

- CLS: 0.00

- Simulated mobile (Fast 3G + CPU 4x slowdown)

- LCP: 918 ms

- CLS: 0.00

- LCP breakdown (desktop sample)

- TTFB: 6 ms

- Resource discovery/loading: 29 ms (discovery 24 ms, download 5 ms)

- Render delay: 442 ms (~92.6%)

- LCP element: post/123-markitdown/Pasted-20250907_...png (non-blocking load, h2, 200)

The data above comes from this lab sampling; there is no CrUX field data in the actual measurement. Reference pages and content come from elements such as the site homepage navigation and article cards; see the site homepage content snapshot and link: site homepage.

### Conclusion

- Excellent metrics: LCP < 1s (desktop/mobile), CLS = 0, overall loading chain is simple (static site, CDN caching effective, h2).

- The main bottleneck is "render delay", not network or resource download. This shows the first screen is mainly spent on style computation/layout/paint, not the request chain.

### Suggested Optimization Directions (by priority)

- Critical rendering path optimization

- Optimize the first-screen DOM size and style complexity to reduce reflow/repaint overhead (list cards, image container shadows/rounded corners/filters, etc. can be reviewed).

- If web fonts are used, ensure font-display: swap to avoid render delay caused by delayed first-screen text painting.

- Image strategy

- Keep the LCP image "accessible" and non-lazy-loaded; if the size is too large, consider explicit width/height dimensions and priority hints (for supported frameworks).

- Enable lazy loading loading="lazy" and decoding="async" for non-first-screen images to reduce first-screen decoding and layout pressure.

- CSS and third parties

- Split CSS reasonably, ensure first-screen critical styles are inlined or prioritized, reducing render blocking.

- Review third-party scripts and analytics, defer non-critical script execution or use defer/async, keeping the main thread for first-screen painting.

- Caching and delivery

- Keep long caching for static assets (cache-control: max-age=600, etc. already seen); if content is stable, it can be extended with fingerprints.

- Confirm images are delivered via adapted formats (such as WebP/AVIF) with appropriate resolution/compression.

### Suggested Follow-up Verification

- On real mobile devices, use Lighthouse to test "cold start/second visit" separately, focusing on FCP, INP, and LCP fluctuations.

- Repeatedly sample different article pages (containing many images/code blocks), observing whether the LCP element changes and whether render delay increases.

- Introduce a performance budget, set thresholds for image size, CSS/JS size, and request count, and check automatically in CI.

Conclusion

Through the above attempts, we can see that Chrome DevTools MCP, in driving the browser to execute via AI, not only has the automated intelligent execution capability we emphasized before, but also has lower-level “debugging” and “diagnosis” capabilities. When selecting AI automation tools, it is worth considering as a preferred direction.

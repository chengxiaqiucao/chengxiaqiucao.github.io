Automated Testing for Browser Extensions - From Install to Popup to Version Migration

11 minute read
中文

Testing a browser extension is not the same thing as testing a web page. Besides page rendering, you may also need to prepare the extension’s own stored data, open its popup, options page or side panel, trigger browser-level events, and verify that old data migrates correctly on version upgrade. The official extension guide gives you a starting point: launch the browser with the extension loaded, wait for its service worker, get the extension ID. But the test logic that really concerns the extension still needs a set of fixtures and helpers behind it.

This article uses one concrete extension as a sample and covers three of the most common and most easily missed scenarios: install behaviour, popup interaction, and data migration on version upgrade.

The Sample: A To-Do List Extension

The sample extension is a simple to-do list. After opening the popup the user sees a task list, can add entries and can delete completed entries:

An example of the to-do list in the popup; task data lives in chrome.storage.local

Tasks are stored in chrome.storage.local, and the popup reads the saved list and renders it each time it opens. This structure is typical: a background script (background / service worker) handles the logic on install and upgrade, a popup page handles interaction, and storage carries the state between them. What testing needs to cover is exactly the linkage among these three.

Environment Setup

Install the dependencies first:

1
2

npm install -D @playwright/test playwright-webext
npx playwright install chromium

Then build the extension into the dist directory and point the Playwright config at the build output:

// playwright.config.ts
import { defineConfig } from '@playwright/test';
import type { WebextOptions } from 'playwright-webext';

export default defineConfig<WebextOptions>({
  testDir: './test',
  use: {
    extensionPath: './dist',
  },
});

Here is the first value point: once the extension path moves into the config, the test cases themselves no longer need to care about “how to get the extension into the browser”. The parts the official approach leaves to you – launching the browser with a persistent context, waiting for the service worker to be ready, resolving the extension ID – are converged into the fixture.

One reminder: extensions can only be loaded in a persistent context, which is the premise of the official Playwright extension approach. When using headless mode in CI, first confirm that the headless mode you use supports loading extensions, otherwise you get false green where the extension is not installed yet the assertions still “pass”.

Case One: Install Behaviour

The most basic class of scenario is the side effect at install time. The sample extension writes the current date into storage on install, for statistics:

1
2
3
4
5
6

// background.js
chrome.runtime.onInstalled.addListener(({ reason }) => {
  if (reason === 'install') {
    chrome.storage.local.set({ installationDate: new Date().toISOString() });
  }
});

The corresponding test is a single assertion:

1
2
3
4
5
6

// test/install.spec.ts
import { test } from 'playwright-webext';

test('saves the installation date', async ({ extension }) => {
  await extension.storage.local.expect('installationDate').toMatch(/^\d{4}-\d{2}-\d{2}/);
});

The extension fixture installs the extension automatically before each test; storage.local.expect() waits for the install callback to write the value, then matches a timestamp starting with YYYY-MM-DD. That “wait” is crucial – the install callback fires asynchronously, so reading storage directly will almost certainly read an empty value, which is also the most common source of false failures when writing extension tests by hand.

Run it:

1

npx playwright test

Chromium runs in headless mode by default and results print straight to the terminal. To watch execution in a real browser, add --headed:

1

npx playwright test --headed

If the extension does not write the installation date as expected, the test fails explicitly and points at the assertion content. Compared with “run it once and see whether anything errors”, this kind of assertion turns install timing into a regressible behaviour contract.

Case Two: Popup Interaction

The second class of scenario is the popup. The approach is to prepare two tasks in storage first, open the popup and verify they get rendered, then delete the first one, and finally verify only the second remains in storage:

// test/popup.spec.ts
import { expect } from '@playwright/test';
import { test } from 'playwright-webext';

test('shows saved tasks in the popup', async ({ extension }) => {
  // prepare 2 tasks in storage
  await extension.storage.local.set({
    todos: ['Buy groceries', 'Read a book'],
  });

  // open the popup and check the tasks are visible
  const popup = await extension.openPopup();
  await expect(popup.getByRole('listitem')).toContainText([
    'Buy groceries',
    'Read a book',
  ]);

  // delete the task
  await popup.getByRole('button', { name: 'Delete Buy groceries' }).click();

  // check the storage for remaining task
  await extension.storage.local.expect('todos').toEqual(['Read a book']);
});

extension.openPopup() returns an ordinary Playwright Page instance, so inside the popup you can keep using the locators and assertions you know. toContainText waits automatically for the tasks to appear in the popup, and it allows extra entries in the list while requiring these two to appear in the given order.

This case also establishes a cross-interface verification chain: write storage → render UI → interact → write back to storage. Asserting only on the UI misses the “data was not saved” defect, asserting only on storage misses the “rendering is broken” defect, and only both together are complete.

After the run you can open the HTML report, walk back through each step with the trace viewer, and look at the page screenshot of every step:

Popup screenshots in the trace viewer, replaying each test step

One implementation detail worth knowing: the popup opens as an ordinary tab, not as a native browser popup bubble. That is a workaround for a Playwright limitation – the Page API it supports cannot expose the native popup for interaction. In the vast majority of cases an ordinary tab is perfectly acceptable, and it actually lets popup content be tested with the full locator capability.

Case Three: Version Upgrade and Data Migration

The third class of scenario is more advanced and is also a hotspot for production incidents: releasing v2 changes the storage format.

In v1 tasks are saved as an array of strings:

1

{ "todos": ["Buy groceries", "Read a book"] }

In v2 they become an array of objects:

1

{ "todos": [{ "name": "Buy groceries", "done": false }, { "name": "Read a book", "done": false }] }

The migration logic lives in the upgrade callback, and the test can be written like this:

// test/migration.spec.ts
import { test } from 'playwright-webext';

test.use({ extensionAutoInstall: false });

test('migrates todos from v1 to v2', async ({ extension }) => {
  // install the old version
  await extension.install('./test/dist-v1');

  // populate the storage
  await extension.storage.local.set({
    todos: ['Buy groceries', 'Read a book'],
  });

  // upgrade to the new version
  await extension.upgrade();

  // check the migrated data
  await extension.storage.local.expect('todos').toEqual([
    { name: 'Buy groceries', done: false },
    { name: 'Read a book', done: false },
  ]);
});

Two key points: put the v1 build output in a separate directory (such as test/dist-v1) while v2 stays in the configured dist; and use test.use({ extensionAutoInstall: false }) to turn off automatic install so the test can install the old version manually first. extension.upgrade() keeps the data already stored by the extension and triggers the upgrade callback, v2 converts the strings into objects in that callback, and the storage assertion waits for the result to appear.

What this case guarantees is that “existing users still have their tasks after upgrading”. If this class of defect reaches production it affects every existing user, and it is usually not rollbackable – the data has already been rewritten by the new version.

Four Hard Parts of Extension Testing, and How to Handle Each

Abstracting the three scenarios above, extension testing differs from ordinary web testing mainly in four hard parts, each with a corresponding treatment.

State lives on the browser side, not in the page. Extension data sits in chrome.storage, IndexedDB or the chrome.runtime context, page refresh does not reset it, and test cases easily pollute each other. The treatment is to turn “prepare storage data” into an explicit test step (such as storage.local.set above) and to have the fixture reinstall the extension before each test, guaranteeing a clean starting point.

Async callbacks have no observable completion signal. There is no hint in the UI when the install or upgrade callback has finished. The treatment is to use storage assertions with waiting semantics (expect(...).toMatch(...) polls until it matches or times out) rather than one-shot read assertions.

Native interfaces cannot be interacted with directly. Popups, side panels and options pages each have their own way of opening, and the native popup cannot be operated with the standard Page API at all. The treatment is to use the wrapped open methods and accept the compromise that “the popup opens as a tab”; at the same time, shift the weight of assertions to the data side and verify only key rendering results on the UI side.

Version migration lacks historical data. Migration logic only runs when old data exists, so a fresh-install test can never cover it. The treatment is to keep the old version build output in the repository as a test asset (such as test/dist-v1), and in the case install the old version, seed the data, then upgrade.

Division of Labour With the Official Extension Guide

The official guide solves one thing – “getting the extension into the browser” – in three concrete steps: launch Chromium with a persistent context, wait for the extension’s service worker to be ready, resolve the extension ID generated by this installation (which may differ each time). None of these three can be skipped, and they are exactly where hand-written extension tests get stuck first.

What the wrapper library does is sink those three steps into the fixture and then add the capabilities extension scenarios really lack: read/write of chrome.storage with waiting assertions, methods for opening native interfaces such as the popup, and the version migration flow of installing an old version and then upgrading. The division of labour can be judged like this – if you only need a few cases on an ordinary page with the extension loaded, the official approach plus a little glue code is enough; as soon as storage assertions, popup interaction or version migration are involved, the amount of glue code quickly exceeds the business assertions themselves, and that is when you should use a wrapper.

Conversely, do not expect a wrapper to solve everything. Cross-browser support is limited by extension loading capability itself (Chromium-based browsers work, other engines need verification first); native popup bubbles, browser toolbar buttons and context menus are outside the coverage of the Page API and still rely on indirect assertions or manual verification. Writing these boundaries into the test strategy is far cheaper than hitting the pit later and reworking.

What to Automate and What Not To

Investment in extension testing should concentrate on three high-leverage scenarios: data side effects at install and upgrade (a defect affects all users and cannot be rolled back), consistency between storage and UI (a broken link on either the write or the render side is a serious defect), and cross-version migration (a hotspot for production incidents). All three share the traits of “happens repeatedly + expensive to fail + deterministically assertable”.

Conversely, visual details of the popup, animation transitions, one-off configuration verification, and flows that need a real account system or third-party login have a low return on automation and are better kept in the manual regression checklist. The criterion is direct: when this case fails, can you say clearly what broke without opening a browser? If you cannot, do not automate it yet.

A Few Things to Watch When Putting This into CI

Build output must be generated before the tests, and its path must be declared explicitly in the config, to avoid “testing the previous version of the code”. Migration tests need build output for several versions at once, which makes the output directory grow, so name artifacts by version and keep only the necessary historical versions.

Verify first whether headless mode can load the extension; if not, switch to headed mode with a virtual display in CI. Tests must run serially or be strictly isolated, because they share the storage area of the same browser profile – this runs counter to the intuition from ordinary Playwright tests that “each case gets an independent context”, and it is the easiest pit to fall into.

Keep traces and screenshots as failure artifacts. When an extension test fails there is often neither a UI error nor a console log, and the storage snapshot and page screenshot in the trace viewer are the only source of clues.

Finally, take the three cases “install - popup - migration” as the minimum baseline, then add business-specific scenarios. They cover the risks unique to the extension form, while business scenarios cover the product logic itself, and the two cannot substitute for each other.

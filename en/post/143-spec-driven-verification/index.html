Keeping the Acceptance Criteria Away From the People Who Write the Code - Conclusions After 967 Runs

Oct 28, 2026
13 minute read
中文

There is a rule repeatedly validated in safety-critical fields: the people who build a system must never be the people who verify it. It is not bureaucratic ceremony but a precondition of verification validity – if a person implements according to their own understanding and then verifies according to their own understanding, the two understandings are naturally identical, and verification degenerates into self-confirmation.

When the coding work is done by an AI agent, this rule runs into a new situation: the same model can write the code, write the tests, and also deliver the conclusion that “all tests pass”. So a question worth taking seriously appears – is there a way to enforce this rule inside a machine pipeline, rather than only writing it in a standard.

Splitting a Spec Into Two Halves

One approach splits the spec file into two parts: requirements and acceptance criteria. The coding agent only receives the requirements part, and the acceptance criteria are cut off before the file is handed over; a separate, independent testing agent writes tests based only on the acceptance criteria and does not read the implementation code.

The two agents run in the same pipeline, but the information they see does not overlap:

The two information channels do not overlap and only meet at the test failure message

  • Coding agent: requirements + test data, no acceptance criteria;
  • Testing agent: requirements + acceptance criteria + test data, no implementation;
  • The only place the two meet is the failure message returned after the test run.

The key is that the “cut off” step happens in code, not by asking the model in a prompt to be self-disciplined. It is a pipeline property that can be demonstrated and audited, not a promise.

One Complete Run: The Failure Message Is Just One Line

Looking at a fragment of a real run is more useful than describing it.

The task is: read recorded radar samples, reject invalid samples, compute the time headway to the vehicle ahead, and warn when the headway is below two seconds. Based only on the requirements, the coding agent wrote this range check – it kept the upper bound but let the zero-gap case through:

1
2

if gap_m < 0 or gap_m > 250:
    rejected.append(...)  # the row, with a reason attached

And the test fixture CSV contains a row S005, a radar sample whose gap is exactly 0 metres. The test generated from the acceptance criteria requires that row to be rejected, and it was not:

1

E AssertionError: 'S005' was not rejected

That is the entire feedback the coding agent gets: which test failed and what the test asserted, with no hint about the underlying rule. The model inferred from it that an exactly zero gap is not a valid measurement.

Then it produced a PATCH changing one character:

1
2

- if gap_m < 0 or gap_m > 250:
+ if gap_m <= 0 or gap_m > 250:

From writing the test to all stage suites going green, the whole round took under a minute, with fewer than ten model calls and a cost of a fraction of a cent. But what really deserves attention is not the speed but the causality: the agent tightened the lower bound because a test it had never seen put the 0-metre gap into the “must reject” pile, not because some written standard told it that zero is invalid.

Had it seen that standard directly, it would have written the correct check on the first attempt and the suite would have passed the first time – and that green result would prove nothing, like a student scoring full marks on an exam they set themselves.

The Easiest Mistake: Hiding a Decision in the Acceptance Criteria

The run above actually comes from the second version of the task. The problem exposed by the first version is more worth recording, because from the outside it looks a lot like “keep editing the spec until it passes”.

The first version’s requirements only said: warn when the headway violates the “two-second rule”. The question “should a headway of exactly 2.00 seconds raise a warning” was placed in the hidden acceptance criteria:

1
2
3
4
5

# Version 1. The boundary is settled in the half the coding agent never sees.
requirements:
  - "Flag a sample as following too closely when its time headway breaks the two-second rule"
acceptance_criteria:   # cut before the coding agent is handed the file
  - "A headway of exactly 2.00 s does not raise a warning"

Back to that criterion: given only the requirements, would two competent developers disagree about 2.00 seconds? Very easily. “Breaks the two-second rule” can be read as “below” or as “not above”. That is a decision, and a decision hidden inside the test criteria is exactly the mistake this split is meant to avoid.

The first batch of runs showed the cost: only three of ten random seeds converged. For the other seven, the agent writing the tests resolved the ambiguity the wrong way and wrote a test that warns at exactly 2.00 seconds – which contradicts the acceptance criterion it was itself given. That is worth pausing over: the testing agent held both the vague requirement and the clear acceptance criterion, and still went the wrong way. A requirement loose enough to support two readings does not just make the coder guess; it also drags the test writer away from the criterion it was given. And no implementation can pass a test that contradicts its own criterion.

The correct fix only moves the decision itself, and only the decision. The acceptance criteria kept every consequence derived from that decision, and the other speed and gap constraints were not touched by a single character, including “zero gap must be rejected”. Nothing was weakened and nothing was deleted.

After moving that one sentence, the same ten seeds converged in all ten cases on the first sweep; the zero-gap fix above still occurred in seven of them, again caught by a test the coding agent had never seen.

The Line Between Fixing the Spec and Lowering the Bar

There is a very fine but very important line here.

Moving a decision that the coder needs is a correction the spec owed all along, and it can justify itself with the single question “would two competent developers disagree”, without looking at any code. Whereas deleting that criterion, loosening it, or copying its boundary value into the requirements would also make the run pass – but then nothing is proven.

This line is especially dangerous in the AI era because the cost of “make it green” has been pushed down to a single conversation. When tests do not pass, the least effortful option for an agent is often to change the test or the criterion rather than change the implementation. The pipeline must carry a hard rule: when tests do not pass, you may change the implementation, you may change the wording of the requirements, but you may not loosen the acceptance criteria. What the tool does at this point is – exit non-zero when a run does not converge, name the tests blocking it, and deliver nothing.

What Changes When the Code Already Exists

Everything above assumes the implementation is written during this run, which is the only situation where isolation can truly be enforced: one process drives both agents and the acceptance criteria are stripped out of one side’s prompt by code.

But most code in the real world is not like that. It already exists, written months ago by a person or by an assistant, and the team wants “this piece of code checked once”.

The same two-agent workflow can point at existing code, with the suite still generated from the criteria by an agent that never read the implementation. What changes is the weight of each outcome:

OutcomeCode written during the runCode that already exists
Test failsA real findingStill a real finding
Test passesThe code satisfied a criterion it never sawThe code agrees with a criterion its author may have seen

Failure is reliable in both cases, because the test was written from the criterion without reading the implementation, so any mismatch is a real divergence between code and spec. Only “pass” weakens, and it weakens for a reason unrelated to the tool: the person who wrote that code may have had the acceptance criteria open in a window next to it at the time.

This is a claim about timelines, so it is worth drawing clearly. For existing code there is no way to enforce order after the fact; the only thing you can ask is version control, which has been taking notes all along:

1
2
3

criteria file, last commit ───────────┐
                                      │ in this order, the criteria were
implementation, first commit ─────────┘ not written against code that was already in the repository

A run against existing code now asks exactly this question, and prints the answer together with its limits – because the limits are most of the truth. A commit date is not a writing date: code can sit in a working tree for weeks without being committed, so this ordering narrows the risk that “the criterion was reverse-engineered from the code” but does not eliminate it; and the criterion being committed first says nothing at all about whether the developer was allowed to read it before implementing.

So this evidence is most valuable when the result is bad: a criterion revised after the code landed is a question someone should answer. That asymmetry matches the table above – better to deliver a check that states its own limitations than to print a green tick that lets the reader believe it proves more.

Version control does know, and can state clearly, one thing: who committed each side. Two different people, which is exactly the separation of duties the whole method borrows.

The Numbers From 967 Runs

The evidence so far is this: on the tool’s built-in sample task, three batches totalling 967 runs (using a small, cheap model so the sweeps could be repeated affordably) produced code that passed all integration and system tests in about eighty percent of runs, and passed every stage including unit tests in about sixty percent. After hardening the process and making the task harder in two places, a fourth batch of 390 runs reproduced the same two numbers.

That number is listed separately rather than merged with the earlier batches – describing two different systems with one number is exactly how results get retracted later. Also, these runs used a cheap model, so both percentages should be read as a lower bound on performance.

The gap between the two stages comes mainly from unit tests, which run last and are the strictest. Most of the remaining problems can be covered by two questions:

  • If the FIX and PATCH produced on each iteration are nearly identical, the agent is guessing at a decision nobody told it – the problem is in the spec;
  • If a rule cannot be triggered at all by your sample data, you get a test that passes no matter how the code is written – the problem is in the data, not the code.

Edge Cases and Experimental Design: Why “Passes on Average” Is an Illusion

The concrete form this separation-of-duties principle takes in a production driver-assistance project is the edge case. One class of problem recurs: the perception module met the requirement – as the developers themselves understood it – but did not measure what really needed measuring.

A detection accuracy requirement will state that the system must stay within some bound. The implementation team read it as “the average accuracy across one recorded drive”, a very natural reading when you are building as you go, and their own tests matched that reading. An independent team comparing the same data against ground truth based on the requirement itself (rather than the developers’ reading) exposed failures that average accuracy over a whole drive can never reveal.

For example, the acceptance criteria would ask: does it hold on every single frame? Including those frames where a vehicle cuts in from the edge of the sensor field of view, or some occlusion occurs. Averaged over the whole drive, such modules pass easily; frame by frame they do not, because thousands of easy frames drown out the few dozen that determine whether the system is safe. The requirement never said whether the bound was a mean or a worst case, the implementers picked the reading their code naturally produced, and they honestly verified themselves against that reading. Developers usually do not have the time or resources to check every edge case personally, and tend to verify a few important scenarios before moving to the next task.

This is the operational design domain (ODD) problem. Defining edge cases accurately and completely in a complex system is an enormous amount of work. The parameter combinations are far too many for brute-force coverage to be practical, and only an ideal oracle could generate perfect coverage over all scenarios. So you need to follow design of experiments (DOE) principles to cover the ODD over the whole test space in an optimal way.

Sample data is evenly distributed in the space, but rare edge regions have almost no coverage points

The same problem reproduced at a smaller scale inside this tool: the faults planted to measure “whether clearer criteria catch more faults” were for the most part invisible to any test suite – because the inputs the acceptance criteria describe never exist in the fixture data. A criterion that nothing can trigger is not a criterion. If the driving data under test never includes heavy rain, then no matter how good the test team is, they learn nothing about heavy rain.

Validation Still Needs a Human in the Loop

One point must be made clear: everything above belongs to verification – given a written criterion, does the code satisfy it, checked by a party that could not see the criterion when it was built. It does not touch validation at all: whether the criterion itself describes what should happen.

A tool can force a coding agent to never see the acceptance criteria. No tool can tell you whether those criteria are the right ones to write. For now that still requires a person who understands the domain, understands the users, and understands why the system exists at all. It also requires writing “correct behaviour” as concrete, checkable descriptions, including the edge cases that careless readings miss. AI can of course assist with all of this, but it still needs human experts to supervise, approve the spec and stay in the loop as the spec evolves.

Three Things You Can Borrow Right Away

First, write “decisions” and “consequences” separately in the spec. Any statement two competent developers would disagree about is a decision that must be settled on the requirements side; the acceptance criteria keep only the checkable consequences derived from that decision. The test is simple: read the requirement and ask yourself whether two reasonable readings exist.

Second, add a hard constraint to the pipeline – do not allow loosening the criteria when a run does not converge. Changing the implementation is allowed, clarifying the requirements is allowed, but “delete or loosen an acceptance criterion” becomes an action requiring human approval. Without that constraint, an agent will always take the least effortful path.

Third, check that your test data can trigger every rule. When you write a criterion, ask at the same time: which row of sample data would make this fail? A criterion with no answer to that is not a criterion.

More fundamentally, verification and validation are not two steps in a process but a professional mindset about “who has the right to answer which question, and why”. What deserves vigilance is not trust itself but methodological omission: a check performed by the builder is not really a check. That holds whether the builder is a person rushing a deadline or an LLM with a context window and a budget limit, and it will still hold in the next generation of software development.

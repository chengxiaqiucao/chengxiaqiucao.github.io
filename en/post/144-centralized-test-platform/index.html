250,000 Test Runs a Day - Architecture and Trade-offs of a Centralized Test Execution Platform

Test automation is usually discussed as a framework problem. But when thousands of repositories all need to run their own suites, the nature of the problem changes – it becomes an infrastructure problem. When every team pushes at nine in the morning, who gets execution capacity? When the nightly full regression collides with the pre-merge check blocking some developer, which one runs first? And when a good portion of failures are not real defects, on what basis do you declare a build “certified”?

One class of platform grows out of exactly this pressure: it does not help you write tests, it provides a shared execution and certification infrastructure. This article breaks down the architecture, key policies and real trade-offs of such a platform, with data from an instance that runs about 250,000 automated test executions a day across four Amazon EKS clusters and serves all engineering repositories of a large financial institution.

Start by Seeing the Five Characteristics of the Workload

Before designing, you must acknowledge that a test execution workload has several properties that break naive designs:

Extreme bursts. Demand spikes during working hours and release windows, while capacity sits idle the rest of the time – always swinging between “not enough” and “wasted”.

Mixed urgency. A pre-merge check holds up one engineer’s time, the nightly full regression holds up nobody’s, yet both compete for the same pool of resources with completely different latency requirements.

Heterogeneous tenants. Different teams bring different runtimes, browser stacks and data dependencies; a suite with no resource constraints can starve every other suite.

Untrustworthy signals. Empirical research shows that async waits, concurrency and test order dependencies keep producing flaky results. Public engineering experience reports that about 1.5% of test runs produced flaky results and nearly 16% of tests showed some degree of instability. Apply that ratio to 250,000 executions a day and 1.5% is about 3,750 misleading results – if retries, classification and quarantine are not platform-level policies but per-team improvisation, then “red” loses its meaning entirely.

Audit requirements. In a regulated environment, “this build passed certification” must be reproducible from records, not from memory.

Three Kubernetes Primitives Carry Most of the Design

Such a platform usually relies on only a few Kubernetes capabilities:

  • Job’s Indexed completion mode: each Pod gets a stable index, which maps naturally onto a test shard;
  • PriorityClass: a high-priority Pod that cannot be scheduled can preempt lower-priority Pods;
  • ResourceQuota and LimitRange: limit how much a namespace can consume and set default requests, avoiding unbounded containers on a shared cluster.

On top of that, queue managers such as Kueue provide queue-level quota, deciding whether a job waits, is admitted or is preempted; autoscalers such as Karpenter provision nodes directly for Pods that cannot be scheduled.

Architecture: Control Plane, Execution Plane, Results Plane

The platform separates three things: “deciding what to run” (control plane), “actually running it” (execution plane) and “turning execution into decisions” (results plane).

Control plane, execution plane and results plane are separated, yet the three must be built as one system

Submission. Each team’s CI system triggers a run, declaring the suite, the target environment and an urgency class. Teams never touch Kubernetes directly – the submission API is the contract, so execution details can be replaced without affecting callers.

Admission and queuing. Each tenant gets a namespace with a quota and a local queue. The queue manager suspends workloads until quota is available, and performs preemption and fair sharing within a cohort (capacity pool): idle capacity borrowed by one team can be reclaimed when another team needs its own share. A borrowing cap prevents a single tenant from swallowing the whole pool during a release sprint.

Shard planning. Large suites are cut into shards and executed as an Indexed Job, with the shard index exposed to the runner through an environment variable – the same contract as Bazel’s TEST_TOTAL_SHARDS / TEST_SHARD_INDEX.

Execution plane. Four EKS clusters host the platform’s 40 applications plus a large number of ephemeral test Pods. Multiple clusters trade higher control-plane and tooling costs for isolation and a smaller blast radius – a trade-off explicitly documented in multi-tenant designs. Placement policy needs deliberate design: give each tenant a “home cluster” where image caches and test data stay warm; when the home cluster’s queue time exceeds a threshold, the control plane spills the entire run to another cluster rather than splitting one run across clusters – splitting makes result collection and infrastructure failure attribution extremely hard.

Results and certification. Each shard sends structured result messages to a reporting and insights service, which decides pass/fail per suite, identifies flakes, and registers a certification verdict on the release. The most important contract in the whole platform is this event schema:

The cohort lets teams borrow idle capacity, reclaimWithinCohort lets the owner take capacity back, and borrowingLimit stops any single tenant from draining the whole pool during a release sprint.

        resources:
          requests: { cpu: "2", memory: 4Gi }
          limits:   { memory: 4Gi }

A few details are worth copying directly: backoffLimitPerIndex retries only the shard that failed and does not rerun the other 39, which matters a lot when a shard hits an infrastructure failure; memory must have a limit, because one OOM runner on a shared node drags its neighbours down; CPU has no ceiling above the request, to absorb short bursts.

One more thing that is easily overlooked: shards should be cut by historical execution time, not by test count. A suite’s completion time depends on its slowest shard, not on how many cases a shard contains.

Latency Comes From Three Waits, Each With Its Own Lever

Run latency is basically made up of three segments of waiting, and each has a different optimisation lever and cost:

WaitLeverCost
QueueingRaise nominal quota, cohort borrowingReserved idle capacity
Node provisioningWarm buffer nodes, pre-pull runner imagesPaying for idle nodes
Slowest shardTime-based sharding, more shardsPer-Pod startup overhead

Autoscalers do well on this kind of spiky and varied demand, because they provision nodes directly against pending Pod requirements; traditional node-group approaches still work when designed properly. Whichever you choose, keep the runner image small and cacheable – at this scale, image pull time is paid tens of thousands of times a day.

Security: Test Code Is “Semi-Trusted Code”

Test code executes whatever a repository commits, so it cannot be treated as a trusted workload. Practical points include: have Pods follow the Restricted security standard as far as possible; use namespaces plus RBAC to ensure one team’s service account cannot read another team’s jobs; access cloud resources through IAM Roles for Service Accounts or EKS Pod Identity rather than long-lived keys; keep test credentials in a secrets management system with least-privilege access; scan runner images and pin their versions. In regulated settings, test environments must also be isolated from production data through network policies rather than by convention.

A Typical Failure Scenario: Release-Day Morning

Three teams submit full regression suites just before the release cutoff, while dozens of engineers are running pre-merge checks.

Without quotas, the first regression suite to arrive would fill every available node, pre-merge checks would queue, and development across the whole organisation would stall. With the design above: each regression suite runs within its team’s nominal quota plus a limited borrowing allowance; pre-merge Pods carry a higher priority class and preempt overnight-grade work when nodes run short; the autoscaler adds capacity for the remaining backlog. The result is that regression suites finish later than they would on an empty cluster, but no single team can slam the brakes on everyone. That is the trade-off a shared platform offers.

Trade-offs and Limits, Which Must Be Stated Up Front

Centralization creates a team everyone depends on: its roadmap becomes the bottleneck and one of its failures stops every release at once. Multiple clusters reduce the blast radius but multiply upgrades, plugin versions and configuration drift. How much each team should get is fundamentally an organisational question – the scheduler does not solve it.

Automatic retries also mask real intermittent problems: a race condition in production code looks exactly like a flaky test. If you retry everything, the two can never be separated.

Why not use the parallelism built into the CI system? Because runners allocated per pipeline serve one repository at a time; they cannot achieve organisation-level fair scheduling, cannot attribute infrastructure failures uniformly, and cannot produce a single certification report. A centralized platform solves these things at the cost of team autonomy. For a small team with few repositories, or for jobs that need special hardware and cannot stay warm in a shared pool, it is the wrong choice.

Five Lessons From Production

Distinguish infrastructure failure from test failure at the source. If a node eviction and a failed assertion produce the same shade of red, teams stop trusting the platform fast. The runner should report the failure cause as a first-class field: test, environment or platform.

Retry once, on a different Pod, and record it. Retrying once on different infrastructure separates environmental noise from deterministic failure. Silent, repeated retries only raise cost and bury genuine concurrency defects – and concurrency is the number one root cause of flakiness.

Quarantine is a workflow, not a switch. A quarantined test must have an owner, a ticket and an expiry date, otherwise the quarantine list keeps growing until the word “certification” means nothing.

The reporting layer is the product itself. Teams judge the platform by the results view, not by the scheduler. The reporting and insights service deserves a dedicated engineering team rather than being treated as an accessory.

Onboarding is part of the platform too. When every repository depends on the same execution platform, misuse – unbounded suites, missing resource declarations, retry loops baked into test code – is paid for by everyone. Running continuous delivery onboarding for newcomers is, in effect, as much a platform control as any quota.

Best Practices You Can Copy Directly

  • Expose a stable submission API and never let tenants depend on cluster internals;
  • Give every tenant a quota, a queue and default resource limits from day one;
  • Shard by historical duration; retry by shard, never by whole suite;
  • Publish the flake rate of every suite and trace every run end to end.

Observability must be built at the platform level, not just the test level: instrument the whole path from submission through admission and scheduling to result ingest, so that “why is my run slow” can be answered stage by stage. The core service-level metrics are four: admission time, time to first result, infrastructure failure rate (counted separately from test failure rate), and per-suite flake rate. Delivery impact can be tracked with DORA metrics to see whether the platform really shortened lead time and reduced change failure rate.

The Two Most Valuable Directions Next

One is change-based test selection. Public data shows that the vast majority of tests rarely fail, so “which ones to run” remains the biggest cost lever. The other is AI-assisted triage: it can cluster failures by likely cause, but it should assist the owner rather than auto-quarantine tests – misclassification directly undermines the credibility of certification.

The conclusion can be compressed into one sentence: a centralized test orchestration platform does more than scheduling. It also isolates tenants safely and provides an authoritative record of quality. Kubernetes provides usable primitives – Indexed Jobs, priorities, quotas, queue managers – but what really determines value is policy: which teams get capacity, how failures are classified, and what counts as “certified”. Queues, the failure taxonomy and the reporting layer must be built as one system; if any one of the three is untrustworthy, so are the other two.

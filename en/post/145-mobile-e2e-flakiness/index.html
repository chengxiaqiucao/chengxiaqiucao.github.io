Why Mobile E2E Tests Go Flaky - Four Failure Modes Web Testing Never Meets

Retries are not a fix. Longer timeouts are not a fix. A quarantine list is not a fix. And that shared Slack channel the team set up specifically for "known flaky, safe to ignore", that is even less of a fix.

Oct 28, 2026
12 minute read
中文

Retries are not a fix. Longer timeouts are not a fix. A quarantine list is not a fix. And that shared Slack channel the team set up specifically for “known flaky, safe to ignore”, that is even less of a fix.

Most testing teams agree with these sentences, but the real issue is this: mobile E2E tests are unstable for reasons that are simply not of the same kind as those behind web tests; and every solution borrowed from the web playbook makes the problem structurally worse.

A recurring sequence looks like this: a team takes over an end-to-end suite, adds automatic retries when tests start failing, lengthens timeouts when retries are not enough, and finally stops trusting the cases altogether. Nobody looks when CI goes red, and nobody knows whether it is a real defect or “just another ordinary Tuesday”.

This is not a discipline problem. The problem is that mobile E2E has four failure modes that simply do not exist on the web, and web-first fixes drag the wrong mental model along with them.

Mobile Instability Is a Different Problem

Web automation runs inside a browser. The browser is a sandboxed, largely deterministic environment: the DOM is queryable, animations can be disabled, network requests can be intercepted, and the rendering engine behaves predictably across runs. When web tests go flaky, the causes are long since well studied – async waits, test order dependencies, shared state pollution; every testing textbook covers them.

Mobile automation runs on top of a whole operating system, and that difference invalidates every assumption inherited from web testing.

A mobile app test has to cope with system-level interruptions the test script never triggered; has to cope with a gesture model where “a 10 millisecond difference in click timing changes the result”; has to survive CI emulators that behave differently on the 47th run than on the first; and has to produce consistent results across a device ecosystem that, on Android alone, spans thousands of vendors and dozens of still-active OS versions.

Fixing mobile flakiness with web solutions is like diagnosing an aircraft hydraulic fault with an automobile brake repair manual: the vocabulary overlaps, the physics do not.

Those web-oriented fixes (unified async waiting patterns, isolated test state, enforced test order) are correct for web problems. Applied to mobile, they probably solve half the problem; the other half has different causes and needs different solutions.

The data shows this has not improved as tooling matured. An industry report on mobile development covering three years and more than ten million builds showed that the share of mobile teams reporting flaky tests rose from 10% in 2022 to 26% in 2025. The more complex the pipeline, the worse the instability.

Four Failure Modes Web Testing Has Never Seen

One: Emulator Behaviour Drift

CI pipelines run on emulators, not real devices. An emulator is a software simulation of hardware, and like any software running in a resource-constrained CI environment, its behaviour degrades continuously over the course of a single test run.

At the start of a suite the emulator responds well: GPU acceleration is warm, memory is clean, the virtual CPU has headroom. Forty cases later the same emulator may be under memory pressure, the virtual CPU may be throttling, or it may start dropping gesture events because the event queue is backed up. The test code is identical; the environment has drifted.

Web CI environments do not have a problem of the same scale, because browser instances are lightweight and stateless. An emulator runs an entire mobile operating system: camera drivers, Bluetooth stack, network simulation, GPS simulation – all of it runs even if your test only touches one login page.

The typical symptom: cases at positions 1-15 pass reliably, and by positions 30-50 they start failing intermittently. The developer’s reaction is to add retries; retries occasionally work because the second attempt happens to catch a moment when the emulator state is slightly better; and the root cause – the emulator changed behaviour mid-run – is never addressed.

Two: Gesture Timing Sensitivity

The essence of mobile interaction is the gesture. A tap is not a click and a swipe is not a scroll, and that difference matters far more than it sounds.

A browser click triggers a discrete set of events (mousedown, mouseup, click) that the DOM handles predictably. A mobile gesture is a stream of touch events with time attributes, interpreted by the operating system in context: holding for 100 milliseconds is a tap, holding for 500 milliseconds triggers a long-press context menu; a swipe that starts 5 pixels further left may be recognised as a scroll rather than a swipe on a particular device or OS version.

Automation frameworks do expose gesture APIs, but the underlying timing behaviour differs between iOS and Android, between OS versions, and between emulators and real devices. A gesture command that is stable on a local emulator may fail on a CI host with different virtualisation characteristics. Long lists usually expose this difference first, because a fast swipe crosses a different number of rows each time – which is why infinite-scroll tests usually swipe one step at a time and then wait for the target cell to appear.

The web does not have this problem; click events are abstracted away at the browser layer. Mobile developers have no equivalent abstraction layer and must work directly against an OS gesture model that varies by implementation.

Three: System Permission Dialogs

iOS and Android pop system-level permission dialogs during app flows: camera, microphone, location, notifications, contacts, Bluetooth. These dialogs are not triggered by your test; the operating system decides when to show them based on internal state.

Once a dialog appears mid-test it covers the interface. The script tries to click an element that is now obscured, the click fails, the element is not found, and the test reports a failure that has nothing to do with the code under test.

When the dialog appears is not fully deterministic: a clean emulator state may not show the notification permission on the first run but may show it on the third, because by then the app has been installed long enough for the system to decide it is time to ask. Teams respond by adding “dismiss the dialog” logic to test setup; but system behaviour changes with iOS and Android versions, so a setup script that works on one version silently stops working on another.

This class of flakiness is especially expensive, because the failure report points at the wrong element – the one the script wanted to click, not the dialog that actually blocked it.

Four: Network Conditions and Device Fragmentation

Mobile apps run under network conditions web apps largely avoid: switching between WiFi and cellular, the app being backgrounded mid-request, carrier-specific DNS behaviour, and latency that varies with signal quality.

A test that passes on a WiFi-only emulator may fail on a real device when it switches to cellular mid-flow; a test that handles a 200 millisecond API response may fail in a CI environment whose network simulation is configured differently. These are not async waiting problems but environment fidelity problems: the test environment and real operating conditions do not match.

Device fragmentation amplifies it further. The Android ecosystem stretches from entry-level phones with 1GB of memory running Android 9 all the way to current flagship hardware. A test designed for “a high-spec virtual machine plus an Android 14 emulator” will meet differences in rendering timing, memory management and garbage collection behaviour on real entry-level hardware. Screen density differences alone are enough to make a click coordinate that works on one device miss on another.

Selector-based suites assume the view hierarchy is stable across devices – and it frequently is not.

Why Script-Level Fixes Make Things Worse

Facing mobile flakiness, the standard move is a predictable escalation path: retry first, because it is the least effortful lever; then add timeouts, because more time usually lets emulator drift and gesture timing eventually slip through; then quarantine, because some cases are reliably unreliable and the team simply stops expecting them to pass.

Each has a cost, and none of it shows up on the CI dashboard.

Retries mask real failures. A case that passes on the third retry is a flaky case that got lucky; it may equally be a real regression buried by the retry logic. One widely cited study found that flakiness caused 84% of “pass to fail” state transitions in its test suites – meaning teams that rely on retries are habitually attributing real regressions to “just flakiness”. The confidence signal the suite is supposed to provide is no longer trustworthy.

Longer timeouts slow the suite without touching the root cause. Extending a gesture timeout from 3 seconds to 8 seconds does cover “the emulator needs more time to process gesture events”, but it also adds 5 seconds to every run of that case. A suite of 200 cases with 3 extra seconds of timeout buffer each runs 10 minutes longer overall. A longer feedback loop means developers have already switched to the next task by the time they learn about a failure.

Quarantine postpones the problem to a future that never arrives. “We will fix the quarantined cases next iteration” almost never happens, because fixing them requires understanding the root cause, and understanding the root cause requires environmental investigation that is slower than writing new cases. So the quarantine list grows longer; and the quarantined cases represent real coverage holes – regressions hide in those holes.

The common problem with all three is the same: treating a structural problem as a maintenance problem. Flakiness is not because the team is not careful enough, but because selector-based tests couple cases to UI implementation details, and those details keep changing as the app evolves, the OS updates and the CI environment drifts.

Public data from one engineering team shows that even with heavy investment in detection and monitoring tooling, 15-21% of builds were still affected by flakiness. Detection and monitoring can tell you which cases are broken, but they will not tell you why mobile-specific failure modes keep manufacturing new broken cases.

At some tipping point the ratio flips: a quality team starts out spending 90% of its time writing cases and 10% maintaining them; after the debt accumulates it becomes 10% writing and 90% maintaining. That compression is what the script-level fix treadmill looks like at team scale.

Five Practical Actions That Need No Tooling

Before discussing architecture-level solutions, there are things any team can do immediately that significantly reduce the four failure classes above:

  • Run each case on a clean emulator snapshot, or at least rebuild the emulator per batch, directly eliminating the root cause of “drift during a run”;
  • Preset permission state during test preparation (through launch arguments or system image configuration), rather than dismissing dialogs with scripts inside the flow;
  • Wrap gestures in an abstraction layer that always performs the interaction after real rendering state, instead of hard-coded wait constants scattered everywhere;
  • Adopt “single-step swipe plus wait for target to appear” for long lists and infinite scroll, instead of swipes that depend on inertia distance;
  • Tier the device matrix: run 2-3 representative configurations in the daily pipeline, and put fragmentation verification into separate, less frequent but broader batches.

These actions bring the total volume of flakiness down, but they cannot change one fact: as long as cases depend on selectors, UI changes, OS updates and device differences will keep manufacturing new failures.

The Architecture-Level Step: Removing the Selector Dependency

The selector-based model – locating elements by CSS selector, XPath, accessibility ID or resource ID – is precisely where the fragility of mobile cases comes from. Change an attribute and the case breaks; the system changes how the view hierarchy is structured and the case breaks; a layout adjustment moves an element 10 pixels and changes its bounds, and a case based on click coordinates breaks.

The alternative is to identify an element by what it looks like and what it does, rather than by implementation attributes. A “Submit” button is recognisable because it says “Submit”, appears in a particular position in the form, and responds to clicks. When that button is redesigned, moved, or given a different accessibility ID, visual identification can still recognise it the way a human tester would.

Looking back at the four failure modes from this angle, their roots all sit in the selector model:

  • Emulator drift causes gesture events to land on the wrong element, because element positions shift in a degraded emulator state – identifying by appearance does not depend on coordinates;
  • Gesture timing problems are amplified by hard-coded time constants – observe the actual rendering state before interacting and the timing assumption disappears;
  • System permission dialogs interrupt selector-based flows because the script is following an element path that is now obscured – identify by visual object and dismiss the dialog without changing the script for every OS version’s dialog format;
  • Device fragmentation breaks selector-based cases because layouts render differently across devices – identifying by “what the user sees” adapts to layout differences automatically.

It should be clear that this is not a feature you can install on top of an existing Appium or Detox suite, but a different test execution architecture: the user flows the cases verify stay the same, but they no longer depend on the implementation details that made those flows hard to maintain.

When evaluating this shift, the right question is not “can it eliminate all flakiness” – the answer is no, network faults and genuine environmental problems will still produce failures. The real question is whether flakiness caused by UI changes, device fragmentation and selector fragility (which is the majority of mobile-specific flakiness) becomes something you fix once at the architecture level, or remains a maintenance tax you pay every iteration.

Closing Thoughts

The loop is predictable: flakiness appears → add automatic retries → timeouts grow → the suite slows down → trust erodes → the team stops treating red CI as a signal worth investigating. This is not a discipline failure but the inevitable result of applying web testing assumptions to mobile testing problems.

The reasons mobile E2E fails simply do not exist in web automation. Emulator drift, gesture timing, system dialogs and device fragmentation are all mobile-specific problems that need mobile-specific structural solutions, not more layers of script-level patches.

And the maintenance treadmill has no sustainable pace. It has only one exit.

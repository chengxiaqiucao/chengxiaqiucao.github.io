Failures Hidden by Retries - Turning the 'Passed on the Second Try' in CI into a Triageable Defect Queue

One failure, one pass, final green. This is what most CI pipelines with automatic retries produce every day, and it is also the result where information is most easily lost: the failed attempt gets overwritten in the logs, deleted during cleanup of the successful job, and the team only sees that “this build is green”. The real problem is that the reason the second attempt passed is usually not “random jitter” but some specific state, timing or data condition – and users will run into it in production too.

One approach deserves a full breakdown: write a structured record for every retry at the end of the suite and keep it separately, aggregate it weekly into a list sorted by impact, and then let a coding agent follow the records into the code to locate root causes. It does not aim to “make CI greener” but the opposite – to re-expose the failures that retries pressed down.

Step One: Let the Failed Attempt Survive Success Cleanup

Most CI configurations delete application logs and diagnostic artifacts after a job succeeds. That is reasonable cost control, but it happens to delete exactly the evidence most needed to investigate intermittent failures. The solution is not to keep all logs, but to write a very small JSON file for every test node that retried, at the end of the suite:

{
  "id": "./spec/features/report_spec.rb[1:2]",
  "location": "./spec/features/report_spec.rb:20",
  "description": "renders a synthetic report",
  "failed_attempts": 1,
  "final_result": "passed",
  "first_error": "expected the default window size"
}

Two fields deserve separate mention. id is the unique example identifier the test framework provides, and location is the source line number. Shared examples cause several different test cases to point at the same line, so aggregating by line number alone merges unrelated failures into one lump; keeping both is what allows correct grouping.

This JSON must be written to a directory outside the scope of success-job cleanup and uploaded as a build artifact. With a common CI service, that means adding one line to the config declaring the directory as an artifact; any CI platform has an equivalent mechanism. There is only one hard constraint: even if this test ultimately passes, the retry history must be kept.

The retry policy itself should also be written down clearly: one retry for ordinary cases, two for cases involving a JavaScript browser. The count is not the point; the point is that every retry must leave a clue about why the result changed. Merely increasing the retry count only makes the report quieter, it does not answer any question.

Step Two: Aggregate the Records into a Prioritized Weekly Queue

With records in hand, the next step is aggregation. A scheduled job reads the past week’s retry artifacts through the CI platform API, groups them by example identifier, and sorts descending by the number of distinct pipelines in which a “failed then passed” occurred.

There is a detail that is easy to get wrong here: if a case failed twice within the same pipeline, it counts as only one pipeline. The ranking wants to measure “how many independent builds this flakiness affected”, not “how many times it failed in total”. Keep the first error message, branch name and number of failed attempts alongside for later reading.

One class should be counted separately: cases where all attempts failed. This distinction only describes the observed run outcome and does not mean “the root cause is deterministic” – an intermittent problem can equally exhaust the retry budget, so you cannot use it to attach different labels to the two classes.

When a given example exceeds a configured weekly budget threshold, make the summary job itself fail, borrowing the team’s existing CI failure notifications to push the list in front of people. At that point, hand the report to a coding agent that can read the repository and build artifacts, and the localization phase begins.

Step Three: Seeing Clearly “Why the Second Attempt Passed” - Four Real Cases

The following classes of problem share one trait: the retry did not make the test recover by itself, the retry mechanism happened to reset the state that was causing the error. Without looking at the first failure, you would never know there was a defect in the product.

A Browser Restart Wiped the Window Size Left by the Previous Case

A group of screenshot comparisons failed, reporting a change in screenshot dimensions, and a retry usually passed. The root cause lay in an earlier case: a billing-related test changed the browser window to a non-default size without restoring it, and the later screenshot case inherited that viewport. The retry configuration restarts the browser before rerunning, the window returns to its default size, and the second attempt passes.

The fix is to explicitly set the default window size before every browser case, with cases needing another size changing it themselves. In this case, “the retry passed” actually provided the key clue: since a fresh browser fixed it, the state must have been brought in from outside rather than restored by the logic under test.

An Apostrophe Broke an Auto-Generated cURL Command

A dashboard generates example cURL commands from a template schema, and the tests execute those commands using generated data. The generated fake names occasionally contain an apostrophe, and the inline command wraps the JSON request body in single quotes – the apostrophe ends the shell string early and the command breaks. The next attempt generates a different name, and the command works again.

The same feature also has a downloadable Bash script that puts the JSON in a quoted heredoc, but incorrectly applies the escaping intended for single-quoted arguments, corrupting the request body. The two places need completely different handling: the inline command must escape apostrophes for the shell context, while the JSON inside the heredoc must be preserved verbatim.

The corresponding regression test is well worth borrowing: replace curl with a function, actually execute the generated script in Bash, capture the request body that would have been sent with that function, then parse and validate the original value – without making any network request at all. Replay the fixed and unfixed versions with a synthetic value like Editor's proof that contains an apostrophe: before the fix the inline command fails outright in Bash and the downloadable script runs but the request body cannot be parsed as JSON; after the fix both preserve the text as-is.

The “shortcut” that is easiest to choose here is to change the test data so names contain no apostrophes. That would make the test more stable and keep the product broken for every legitimate input.

A Temporary File Was Collected Before the Render Process Read It

An inline HTML-to-PDF renderer writes header and footer HTML to temporary files and then hands the paths to a render process. The code keeps the temp file objects in local variables while building the command; after the method returns, the command string still holds the paths, but nothing references those objects any more.

Ruby’s Tempfile hooks cleanup onto garbage collection. If GC happens to run before the render process opens the file, the file is already gone. Whether the test passes depends on when garbage collection occurs – the most typical “seemingly random” failure.

The fix is to keep the header and footer objects on the service instance until rendering completes, then close and delete them in an ensure block. The regression test forces GC between “build the command” and “simulate the render process reading the file”, asserting that the file content is still readable and gets cleaned up afterwards. Deliberately manufacturing a deterministic failure condition is far more reliable than waiting to get lucky in some PDF case.

Ruby’s Clock Was Frozen, Redis’s Clock Was Still Running

A rate-limit test uses counters that count within a fixed time window. Once a case crosses the window boundary, requests get counted into the new window and the expected threshold is never reached. The first fix frozen the process clock, but the counters live in Redis with an expiry time, and Redis keeps running on real time. If you freeze near the end of a window, the counter’s remaining time to live is very short and the problem persists.

The final approach freezes at the start of the hour, aligned with the time window these cases use, so the counter gets a full expiry cycle; the cases still have to finish within that cycle. The value of this case lies in the fact that review found a second clock after the first fix – the first explanation covered only half of the timing mechanisms in the system.

The same investigation round also surfaced several other classes of problem: a background worker still running when database cleanup started; test helper functions overwriting each other’s frozen state on a shared clock library; and a sample data generator using truthiness to decide whether to skip lower-bound adjustment when the bound is zero (in JavaScript 0 is falsy, yet in this schema it is a legitimate lower bound). Each falls into the category of “a retry makes it disappear, but a user may still hit it”.

Step Four: Draw Clear Task Boundaries for the Coding Agent

When handing the weekly report to a coding agent, the task description should be specific enough to be verifiable, not “please take a look at these failures”. A reusable set of requirements is:

  • Find the corresponding CI run and read the failure artifacts, then follow the test code into the application code;
  • Reproduce locally where possible first, then add a regression test that is required to fail before the fix and pass after it;
  • Split unrelated root causes into separate commits, so each can be reviewed and rolled back individually;
  • Run the affected checks and self-review the diff, explicitly listing items that could not be reproduced, without vague hand-waving;
  • Stop and wait for human approval before pushing.

The reason for insisting that “artifacts and code must be read together” is that neither side alone yields a conclusion: a mismatched screenshot size does not by itself explain who changed the viewport, and a missing file does not by itself explain why that Ruby object became collectable. The agent’s real value is joining those two kinds of information, not replacing the human final judgement.

Any rule in the investigation conclusions that “future development must follow” goes into the AGENTS.md closest to the code (or an equivalent team convention file). For example, “browser cases may change their own viewport, but the next case must start from a known size” – setup code enforces it, comments explain why. Better still, anything that can be turned into a static check should not rely on memory: add a custom lint rule for the common flaky patterns and let CI block them, which works far better than hoping someone remembers an investigation from six months ago.

An Action Checklist

If your suite already retries, you do not need to refactor the whole system first. Just follow this order:

  1. At the end of the suite, write one structured record per retry, with fields covering at least the unique example identifier, source location, number of failed attempts, final result and first error;
  2. Put the records in a directory that success-job cleanup cannot reach, and configure it as a build artifact upload;
  3. Aggregate and sort weekly by “number of distinct pipelines with a failed-then-passed”, set a budget threshold, and when it is exceeded make the summary job fail and notify;
  4. Pick one recurring problem and demand a clear explanation of “why the second attempt passed”, rather than simply adding more retries;
  5. The fix must come with a regression test that reproduces deterministically, and only merges into the regular CI, QA and release flow after review passes.

There is no published data yet on hours saved by this process, and the fix rounds are too recent to judge how far it can push the recurrence rate down over the long run – the weekly reports over the coming weeks will answer that. But its immediate effect is already clear: problems that used to require someone to set aside half a day to chase, often losing the trail halfway through, can now be investigated in parallel with other work, and coming back only requires assessing whether the explanation holds and whether the change is reasonable.

That is exactly why the quality of code written by the agent matters more: a reproducible failure and a test that asserts the real intent are concrete targets it can anchor on. And keeping the retry history is equivalent to putting more of those targets on the table.

The Locator Broke but the Test Stayed Green - Runtime Self-Healing and Its Three Audit Gates

A front-end refactor renames a class and moves a button, the application works as before, but half the selectors no longer match. The traditional fix is to have someone update the locators one by one and rerun. Runtime self-healing offers another path: when a selector fails, let a model decide from the elements actually present on the page which one you meant, continue execution after verification passes, and cache the fix so the next run does not call the model again.

The idea sounds like “making tests less brittle”, but the real engineering difficulty is not fixing it – it is that fixing it wrongly also goes green. If the checkout button is removed and the model confidently clicks a different button, the suite is all green and nobody notices the product is broken. So what deserves a breakdown is not the model prompt but the whole mechanism of verification, auditing and cost control – those decide whether self-healing is a productivity tool or a new source of silent failure.

The Six Steps of One Self-Heal

Taking a working implementation from the Playwright ecosystem as an example, one self-heal follows a fixed, observable flow:

  1. Run the original locator first. Give it a very short timeout (1 second by default); if the element appears normally, perform the action directly and the self-healing logic never engages – when matching works, the suite behaves exactly as before integration.
  2. Check the cache. A locator previously fixed for the same page path, same action and same description is tried first. On a hit, no model call happens.
  3. Narrow the candidates. Collect up to 1,000 interactive elements from the page, score and sort them by keyword match, element type, ARIA role and test id, and send only the top 40 to the model. This step prevents the target element from being cut off for being late in DOM order.
  4. The model proposes candidate strategies. It returns at most three Playwright locator strategies – test id, role with name, label, placeholder, text, alt text, title or CSS – each with a confidence score; the output must conform to a fixed JSON schema, not free text.
  5. Verify one by one. To be accepted, a suggestion must satisfy all of: it matches exactly one element, that element is visible, and confidence is not below minConfidence.
  6. Execute and persist. The effective locator is written to the cache file, and this self-heal is recorded as one line of JSONL in the event log, including the model’s reasoning, confidence and token consumption.

“Call the model once per element, not once per run” is the heart of cost control. The cache is organised by action, page path and description, and once committed to the repository the team and CI share the same fixes.

The full chain from short-timeout detection through cache hit, candidate narrowing, uniqueness verification and persistence

Verification Matters More Than Generation, but Verification Alone Is Not Enough

Steps 4 and 5 are the most valuable part of this design: the model does not invent a selector out of thin air but chooses from candidate elements really present on the page, and the answer must resolve to one concrete, visible, unique element. By comparison, “let the model write a new CSS selector” is almost uncontrollable.

But uniqueness and visibility only guarantee that “this element exists and is unique”, not that “it is the one you wanted”. The original article states the risk bluntly: delete the checkout button and if the model confidently picks another button, the test still passes and the defect is silently swallowed. For quality assurance, a self-healing mechanism that never reports a false positive is more dangerous than one that occasionally fails.

Hence three gates are needed to force “self-healing happened” into a visible signal.

Gate One: Confidence Threshold

minConfidence defaults to 0, meaning any score is accepted. In production it should be set explicitly to something like 0.8: when the model is not sure enough, better to let the action fail than to guess. This switch turns “uncertain” back into a red light.

Gate Two: Report-Only Mode

warn mode records “how it would have been fixed” but keeps the original failure; cached fixes are also only reported, not applied. The latter point is especially critical: otherwise a cache file committed to the repository can quietly turn an audit run all green, and the team never sees which selectors should have been updated long ago.

Gate Three: Make the Build Answer for Self-Healing

// global-teardown.ts
export default function () {
  const { healed, entries } = getHealSummary();
  if (healed === 0) return;
  console.error(`${healed} locators need fixing, please update the following selectors:`);
  for (const e of entries.filter((e) => e.outcome === 'healed')) {
    console.error(`  ${e.action} "${e.contextName}" -> ${JSON.stringify(e.strategy)}`);
  }
  process.exitCode = 1;
}

There is a process-model pitfall here: tests run in worker processes and teardown runs in the runner process, so in-memory data is not shared – each result must additionally be written to a JSONL summary file, from which the summary interface reads; and counting must cover only the current run, so if the runner does not exit between runs (UI mode, watch mode), reset the counters explicitly in globalSetup.

The combined semantics of the three gates are clear: self-healing is a temporary means of keeping the build unblocked, not a licence to stop maintaining selectors.

Controlling Cost, Speed and Privacy

Every self-heal calls the model once, and left unchecked the cost and latency rise linearly with the number of failing selectors. Four reusable optimizations:

  • Compress candidate attributes: send only attributes that have values, and use short keys (such as tid for test id and txt for text);
  • Flag hidden elements instead of dropping them: real applications often deliberately hide the target element (custom-styled checkboxes, buttons that only appear on hover), so such elements are sent along with hid: true;
  • Sort before truncating: after scoring by keyword, element type, ARIA role and test id, take only the first maxCandidates, default 40; simple pages can drop to 15, dense pages can rise to 80;
  • Limit output length: the model returns at most three strategies, and token consumption is printed on every self-heal and recorded in the event log, so it can be accounted per team.

The scope of what is sent must also be clear: the model receives a structured list of candidate elements (tag name, role, ARIA labels, text, test id and so on) plus the page URL, and no screenshot and no full page HTML. If the DOM may contain personal information, financial data or internal addresses, the options include using a local model so data never leaves the machine, pointing at a self-hosted gateway, enabling it only in non-production environments, and periodically reviewing what was actually sent as recorded in the event log.

Empirical Trade-offs for Local Models

For a fully offline local inference setup, one set of comparison data has been published and is well suited as a selection reference:

ModelSizeTest resultCharacteristics
llama3.2:3b2.0 GB5/5 passedBest overall: fast, accurate, small
mistral4.1 GB5/5 passedMost accurate but slowest, about 1.4 minutes per run
gemma3:4b3.3 GB4/5 passedFaster than mistral (about 53 seconds), slightly lower accuracy

Small models from 1B to 4B struggle in scenarios like “a row of nearly identical checkboxes”; when accuracy matters, choose a larger model. The cost of the local option is that model latency per self-heal is usually higher than cloud (about 1-2 seconds in the cloud), in exchange for zero API keys, zero data egress and zero call fees.

There is another class of model that does not “generate text” and deserves separate mention: it does not write selectors but answers a multiple-choice question with calibrated probability – among the collected candidate elements, which one is the element you described, and is that element even on the page. The answer can only be an element that really exists on the page, its probability is used directly as the confidence checked against minConfidence, and the locator is then constructed by code from that element’s own attributes. On an evaluation set containing 76 deliberately broken locators (covering buttons, links, inputs, checkboxes, ARIA widgets and hidden controls), this approach fixed all of them; the cost per call is about $0.0001, and a round trip with 40 candidates takes under a quarter of a second. When the description matches no element on the page, it answers plainly “none” and puts the best guess with its score into the error message, so a badly written description is easy to spot too.

The Four Config Options Most Worth Tuning

OptionDefaultTuning advice
quickTimeout1000 msDeliberately short so bad selectors fail fast; raise it if the application really has slow-rendering regions, otherwise “slow” is misjudged as “broken” and a model call is wasted
minConfidence0Set to around 0.8 so uncertainty becomes failure
maxCandidates40Drop to 15 on simple pages, raise to 80 on dense pages; this directly determines tokens and accuracy
maxAiTries4How many suggestions to verify before giving up, used together with the three-strategy output cap

Artifact files need clear responsibilities: the cache file (fixed locators, organised by action / page path / description) should be committed to the repository so the team and CI share it; the event log (reason, confidence, token count of each attempt) and the summary log go into the ignore list; lock files and temporary files likewise. You can also choose not to commit the whole directory and let each machine maintain its own fixes, at the cost of the model being called again on every CI run.

Known Limitations

  • Cloud models need a key and a network; local models need neither but have higher latency;
  • Only the main frame is searched; elements inside iframes are not candidates yet, while open shadow roots can be found;
  • A click with force: true dispatches the event directly without pointer coordinates, so it cannot cover interactions that depend on real pointer position;
  • Parallel workers share the cache through a lock file, which is best effort, not a database;
  • Self-healing is off by default and only takes effect when the switch is explicitly turned on, so suite behaviour is unchanged during early integration and the risk is contained.

A Suggested Integration Order

  1. Keep self-healing off and run in warn mode for one or two weeks first, collecting a list of “which selectors break most often” – that list is itself the debt register of your automation assets;
  2. Fix the frequently failing selectors by hand first and leave the rest to self-healing, so architectural problems do not get hidden in the cache;
  3. When turning self-healing on, set minConfidence at the same time and enable the “any self-heal fails the build” rule in global teardown;
  4. Every change to the cache file goes through code review; treat it as test code, not a build artifact;
  5. Enable it only in non-production environments, and switch to a local model or self-hosted endpoint where sensitive DOM is involved;
  6. Regularly review token consumption and the distribution of reasons in the event log, to judge whether “there are more refactors” or “the descriptions are vague”.

What the self-healing mechanism really solves is the queueing problem during a refactor, when a large number of cases go red at once and people cannot fix them fast enough. What it does not solve, and should not try to solve, is “what the tests are actually verifying”. Make every self-heal a record that must be seen, reviewed and eventually eliminated, and this capability will not degrade into a green light that also flattens real defects.

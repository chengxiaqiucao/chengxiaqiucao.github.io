阅读时长: 7 分钟

一次会话笔记里记着这样一条：0:31，结算页显示支付失败，刷新订单状态后，后端却查到了一个订单 ID。界面和系统对不上，而这类分歧几乎不会出现在脚本用例里——脚本只会问「支付成功了吗」，不会去追一个失败之后系统到底留下了什么。

脚本测试能找到的，是你事先想到的 bug。你设想了一种坏法、写下一条检查，那条检查从此守住这一种情况。这有价值，也是天花板：全绿只说明你预测过的失败没有发生，没预测到的那些依然隐形。登录用例通过，用户改完密码却被卡住；结算用例通过，购物车变了总价却没跟着变；主流程在测试环境正常，真机上按钮卡到让人点了两次。

探索性测试就是用来找这些的。它是有技术的调查：用产品、跟着观察到的东西走、不断问脚本没被交代去问的问题。不是随便点，是一场有任务、有笔记、结尾有证据的会话。

学习、设计和执行同时发生

一个至今仍好用的定义是：学习、测试设计、测试执行在同一时间发生。

容易被跳过的是最后半句。探索不是把结构扔掉，而是用上一条测试刚教给你的东西，设计下一条。如果支付按钮禁用状态持续了四秒，不要继续照原清单往下走，而是问它为什么像卡住：换更慢的网络、点一次然后等、连点两次、在支付请求中把应用切到后台、再查订单被创建了一次还是两次。

会话因为产品反馈而改变，这是它和 ad-hoc 测试的分界。后者没有记忆；探索性会话有任务、有笔记、有证据，结束时得能交代清楚：测了什么、发现了什么、哪些没覆盖到、还有什么不放心、哪些要转成脚本用例、缺陷报告或产品问题。答不上来，刚才就只是在点。

先写一句话章程，不是写一套脚本

动手之前不写长脚本，写 charter——这次会话的任务。一句话就够，比如：在慢速移动网络下探查游客结算，准备一件商品、一张过期卡、一张被拒卡，确认支付失败是否提示清楚、能否恢复、会不会产生重复订单。

这一句同时给出了目标、风险和需要的证据类型。会话因此有了形状：章程指方向，探索时产品反馈决定下一步，收尾落到笔记和复盘。

还要在碰产品之前记下环境。听起来琐碎，但等开发问「哪个构建、哪台设备、什么数据」时，不该靠回忆重建：构建版本、设备与浏览器视口、网络限速档位、账号状态、测试数据、以及本次主风险。示例里写的是 build 482、Pixel 7a、慢速 3G、游客账号、过期卡与拒付卡，主风险是用户无法从支付失败中恢复，或被重复扣款。

用一张真实界面逼出可检验的断言

为什么要用足够真实的界面，而不是一段支付失败处理说明？因为界面会把具体声明摆到你面前：购物车仍已保存、按钮可以再次点击、总价是 $18.25、支付失败所以不该有订单、提示足够让真实用户恢复。

每一条声明都是一个可以立刻去核对的断言。一段抽象描述只能让人点头，界面才能让人注意到这里承诺了什么。于是观察点变成一串明确问题：用户知不知道卡被拒了、重试会不会丢购物车、按钮看起来是不是卡死、后端有没有建单、连点会不会出两笔订单。

60 到 90 分钟，然后开始制造变化

会话要设时间盒，60 或 90 分钟比较合适：够追一条线索，又不至于散成一个下午。

第一遍走通主链路：加商品、以游客身份继续、填配送信息、试过期卡、试拒付卡、用有效卡重试、再核对确认页、邮件、订单历史或能拿到的 API 响应。之后才进入真正值钱的部分——主动改变可能暴露风险的条件：

  • 慢速网络：支付流程常常在技术上失败之前，先让人感觉坏了
  • 连点支付：重复订单和重复扣款最容易在这里出现
  • 支付请求途中切后台：移动端用户天天这么做，产品必须能恢复
  • 支付失败后改购物车：总价和支付状态可能失同步
  • 会话过期：游客态或登录态在流程中间失效时，结算是高危区
  • 结算途中商品售罄：系统无法履约，界面却可能还在展示

目标很朴素：持续问自己，什么会让你不敢发这个版本。

时间戳笔记要让别人能接着查

笔记不需要好看，需要诚实，而且要能被开发、产品、另一位测试直接读懂，最好能让他们明天接着查下去。一份能直接照着写的会话笔记长这样：

  • 0:00 在 build 482、慢速 3G、过期卡条件下开始结算，购物车与 $18.25 总价基线正常
  • 0:08 提交过期卡，拒付提示清楚、购物车保留，恢复信号良好，转去试拒付卡
  • 0:15 提交拒付卡，支付按钮无 spinner 禁用约 4 秒，提一条易用性缺陷
  • 0:24 慢速支付中切后台，回来显示处理中，随后收到确认邮件，去查是否建单
  • 0:31 刷新订单状态，界面说支付失败，后端有订单 ID，提高危缺陷
  • 0:48 失败后改数量，购物车变了但屏幕总价仍停在 $18.25，提数据缺陷

每一行都包含动作、观察、决定和证据。还有一个可对照的真实案例：在一个大型零售平台的购物车上，脚本用例全绿，探索时却发现跨过促销门槛后「再买多少可升下一档」的提示没有跟着更新——脚本只验证了折扣确实生效，没有问边界处那个数字是否仍然正确。

找到高危问题不能让它埋在笔记里。转成缺陷报告时要写全：标题、构建与环境、复现步骤、预期（失败支付不产生订单）、实际（界面失败但后端有订单 ID）、证据（截图、网络请求、订单 ID、时间戳）、影响（游客可能以为没付成功，实际订单已存在）。探索负责发现问题，报告负责让问题可修。

卡住不知道从哪下手时，用透镜

透镜只是防止自己只测最明显那条路的提问框架。数据：哪些值会在我脚下变化（数量、税费、运费、售罄、优惠码）。时间：动作之前、之中、之后各发生什么。状态：用户和系统各处于什么状态（游客、会话过期、购物车已改）。接口：依赖了哪些系统（支付提供方、邮件服务、订单服务）。平台：哪里体验会不同（真机、移动浏览器、弱网）。恢复：用户能不能安全脱身（重试、换卡、回购物车、取消订单）。

其中数据、时间和恢复最容易挖到真正疼的 bug。

哪些发现该变成自动化

会话常常正好告诉你什么值得自动化。判断依据不是看起来厉害，而是能不能给团队带来可重复的发布信心：过期卡给出清晰提示且保留购物车，该自动化，是稳定且重要的恢复行为；失败支付不得建单，该自动化（前提是能通过 API 或测试工具核验订单状态），它保护钱和信任；按钮卡了四秒，更适合作为 UX 问题、性能预算或视觉评审，不必硬写成功能用例；总价在改购物车后不变，该自动化，是可能回归的数据准确性 bug；一句「这个提示有点绕」，保持人工评审，除非文案有明确硬性要求。

AI 在这里能帮上忙，但判断不该交出去。可以让代理把需求文档汇成风险区、起草初始章程、生成测试数据组合、探索时帮忙看网络请求与日志、把笔记整理成规范缺陷报告、推荐值得自动化的候选。不该指望它替代整场会话——屏幕让人觉得卡住、恢复路径让真实用户迷惑、错误提示和实际发生的事对不上，这些仍然要靠人。

一张轻量的会话表和十分钟复盘

表格太重大家就不用了，但该有的字段得有：章程与所追风险、构建与环境、覆盖到与没覆盖到的区域、带时间戳的动作与观察、已提缺陷及单号、阻碍确定性的疑问、后续动作（自动化、复测、继续探索、改进测试环境）。每次会话填一份、格式固定，攒起来才可横向比较。

结束时留十分钟复盘，自己或拉一位同事都行，平实地回答五个问题：学到了什么、证明了什么、还有哪里不放心、什么证据能让我们安心发布、什么该变成可重复的检查。

好的会话结束时，团队手里的证据比开始时更好。章程让它聚焦，笔记让它可信，好奇心负责找出脚本没被交代去找的那个 bug。挑一个高风险功能，写一句话章程，框一小时，边测边记——这就够开始了。

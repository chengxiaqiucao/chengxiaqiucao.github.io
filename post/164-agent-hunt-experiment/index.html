给 AI 代理的指令里加上写下假设和预测，再要求它每观察一步就记录异常信号，它会不会找到更多缺陷？有人把这个想法做成了一次可判定的实验，并且事先写好了预测。结果预测没成立：三组条件下的中位数都是 6 个植入缺陷里找到 3 个，一项都没提升。

更有价值的不是加提示词没用这句结论，而是数据逼出来的一个区分：一份工整的调查日志、调查本身、找到的缺陷、以及没被测到的风险，是四件不同的事。漂亮的日志只证明第一件。

实验问的是一个很窄的问题

前一篇的论点是：能顺利执行步骤的代理，并不等于在做探索性测试。探索是调查，不是脚本；一条用例可以在主路径上全绿，同时漏掉双击产生的重复订单。

于是争论被换成一个可测量的版本：给一个通过浏览器工具工作的通用代理加两处指令结构，看它找到的植入缺陷在数量和类型上是否变化。测的不是代理有没有学会像人一样思考，只是这两处改动的效果。

先做 Pilot，再重做一个应用

第一轮每条件只跑一次，在一个带植入缺陷和诱饵的小型购物应用上，约 40 次工具调用预算。两组都找到 5 个里的 2 个，都漏掉了全部三个时序与并发缺陷，两份报告也都没提到围绕它们的订单延迟。

一次运行分不清是脚手架起作用还是运气好，调用上限还可能决定了它在哪停下。所以第一轮只当 pilot，第二轮换了一个新应用，而不是针对已经看熟的系统调参数——这个决定值得单独记下来， evaluation 里最常见的自欺就是拿见过的题调参。

六个缺陷、四个诱饵、三组条件

新应用是一个小型订票 Web 应用，植入 6 个缺陷、4 个诱饵（看起来可疑但行为正确的设计）：

  • 订 60 张票被截断成 59
  • 旧报价覆盖新报价
  • 两个买家同时拿到最后一张票（检查后才执行的竞态）
  • 重复提交产生两笔订单
  • 非数字数量返回 HTTP 200 且金额为 NaN
  • 被拒绝的订单在界面上什么都不显示

中间三个属于时序与并发缺陷。三组条件分别是：A 默认章程（探索下单流程并报告任何不正确或可疑之处，附复现步骤）；B 在 A 之上要求每个假设都先写预测与可证伪条件；C 在 B 之上增加必做的信号步骤，每次观察后、选下一个假设前，记下延迟、顺序、状态码等意外之处。

图 1｜A/B/C 逐层叠加指令结构，缺陷按单输入可暴露与需时序触发分开归类

设计相当克制：每条件 5 次、共 15 次，分 5 波、每波 3 个并发会话且各含一组条件，槽位与波次顺序用记录下来的随机种子生成。每次会话有独立的应用实例、端口、种子和浏览器配置，统一模型、20 分钟上限。预测、指标、评分规则与判定规则在应用建成、任何运行开始之前就固定下来。两名独立 AI 评分员只看报告、对条件盲评，按答案键打分，90 个判定里分歧 4 个，且在揭盲前裁定完毕。

还差点出事的地方也全部公开：应用前端 JavaScript 的注释里写了三个缺陷，浏览器可直接读到；读权限能拿到缺陷清单和其他条件的提示词；会话之间能互相访问端口；挂起进程可能阻塞结果保存。这四处都在开跑前修掉。跑完之后，评测脚本又把 15 次会话全部标成基础设施失败，原因是它匹配到了每份记录里都会出现的一条常规状态消息——这次是误报。

预测没成立，逐缺陷的数字更有意思

事先写下的预期是：脚手架会有帮助，信号步骤对时序缺陷帮助最大。实际结果：

  • 6 个缺陷的中位发现数，预测 A/B/C 为 3 / 4 / 4，实际 3 / 3 / 3
  • 3 个时序缺陷的中位发现数，预测 0 / 1 / 2，实际 1 / 1 / 1

按预先登记的判定规则：B 的中位数不高于 A 就算脚手架无效；C 的时序中位数要超过 B 才算信号步骤有效。两个条件都没达到。这不等于证明脚手架完全没效果，只说明它没有跨过事先设好的门槛。

评分也做了交代：两名评分员单独给出 2/2/3 与 3/3/3 的不同总中位数（两个缺陷处在边界判定上），但都不改变上述两个预登记决策。C 在其中一名评分员下总数更高属于探索性观察，不是预登记指标，不能拿来当信号步骤有效的证据。

真正稳的结论藏在逐缺陷命中数里（每组 5 次运行，需带可复现触发与证据）：

  • 60 张被截成 59：5 / 5 / 5，也就是 15 次全中
  • 旧报价覆盖新报价：3 / 3 / 3
  • 最后一张票竞态：0 / 0 / 1
  • 重复提交：0 / 0 / 0
  • 非数字数量返回 NaN：5 / 3 / 5
  • 被拒订单无提示：0 / 2 / 3

单输入或单屏幕就能暴露的缺陷几乎次次被找到：上限边界 15/15，NaN 金额 13/15。需要特定交互序列或时序的缺陷极少被找到：竞态 1/15，重复提交 0/15，两名评分员对这两个数字完全一致。旧报价缺陷（需要响应乱序到达）居中，9/15，其中一次判定在边界上。指令结构并没有消掉这道沟。

图 2｜边界值与异常金额几乎全中，竞态与重复提交近乎全漏，两类缺陷之间出现明显断层

耗时中位数 A/B/C 为 155 / 194 / 172 秒，单次成本约 0.16 / 0.23 / 0.22 美元，远在 20 分钟上限之内。这些只作完整性记录，不说明哪种条件更高效。

两种解释，这次实验分不开

低命中率至少有两种说得通的原因，而数据无法区分：

一是能力上限——通过浏览器工具，代理难以构造或推理并发交互；二是策略选择——提示词告诉它「继续投入不值得时就停」，还说有个它看不见的时间上限，而会话其实在两三分钟就结束了，预算根本没用完。

浏览器工具本身是否让并发交互更难触发，也没测过。另外，低发现率只说明结果不够好，不说明调查是在哪一步开始出问题的：可能压根没想到要试并发，可能想到了但没投入，可能触发了却没能识别证据。每一种对应的修法都不同。停止同样得拆成三件事：允许使用的预算（20 分钟）、代理实际的停止行为、以及被写进提示词的停止策略。这次只能确认预算没被用尽。

把四种证据分开看

可以把证据拆成四层（这是提议中的框架，不是已验证模型）：process 是代理有没有记下假设、预测与可证伪条件；investigation 是它有没有真的跑一个能区分可能性的实验；outcome 是它有没有找到并复现缺陷；coverage 是哪些重要风险根本没被测到。

一份整齐的调查日志是 process 的证据，不是覆盖充分的证据。四者指向不同的修复动作：从没考虑并发，是优先级问题；考虑了但触发不了竞态，看工具或执行策略；触发了却没认出来，看证据解读。这次实验并没有把四个维度都测到。

旁证也支持把日志只当流程证据：B、C 被要求在每个实验前记录预测与可证伪条件，而 77 条已记录的预测里，只有 25 条是在浏览器动作之前写入的，其余 52 条首次出现在与观察同一次日志写入中，无法证明预测在先。

一个没被验证的提案：人先定章程

于是问题收窄成一句：谁决定代理在获准停止之前必须查什么？

提案是由人在会话前设定、会话后复核的章程，包含三项：最低风险覆盖（一份必须测试或明确说明为何跳过短清单，如并发下单与重复提交，并规定什么证据算覆盖，由人判定；一个说得通的解释不能替代调查）；不由代理自行判断的停止条件；以及被放弃假设的记录与理由，由人阅读。

要强调的是：这是设计提案、不是发现：让代理必须测并发本身仍是一次提示词改动。如果它有效，说明缺口主要在要求与停止策略上，覆盖决策该留在人手里；如果无效，说明缺口比提示词更深。两种结果都能给出当前数据给不了的信息。而且，人能决定并发是否在范围内、什么算调查充分，并不代表代理就能构造出正确的并发交互、稳定触发或认出竞态。

不依赖代理的那条结论

实验最实用的输出，其实与用什么模型无关：一份测试章程不该只写要探索哪个功能或哪条旅程，还要写明重要的风险类别、什么证据算一次发现、以及哪些风险不允许跳过。无论执行者是人、浏览器代理，还是两者混合，这一条都成立。

边界也要如实说清：每条件 5 次运行、一个模型、一个专门造的应用，只报描述性数字，不主张统计显著；评分员与被测代理来自同一模型家族；C 的提示词点名了延迟、顺序与状态码，提升即便出现也可能来自这个提示而非步骤本身；其中三次会话共用一台内存有限的机器，波次设计只能平衡、不能消除；提示词本身要求填写未调查部分、告诉代理在不值得时停止、还提到一个它看不见的时间限制。至于换个模型、换个应用、拉长会话会怎样，这次数据一句也说明不了。

下一步该一次只改一个变量：固定模型、应用与评分标准，以 B 为基线，只把明确要求并发与重复提交测试加进去，停止策略保持不变，并记录代理是否考虑到每个风险、是否尝试交互、是否触发缺陷、是否读懂证据；之后再单独改模型或停止策略，并增加运行次数。

给代理加上调查结构，不等于给了它调查能力。真正决定结果的，还包括我们要求它查什么、接受什么当证据，以及它停下来时，还有多少未知留在桌上。

花了42 分钟、用了92000 个 token，AI才跑完一次登录

一个无聊的问题，配一个无聊的答案：一台现成的 Mac mini 上跑一个 300 亿参数的本地模型，能不能给自家金融 App 写 Andro…

2026-11-19
阅读时长: 9 分钟

一个无聊的问题，配一个无聊的答案：一台现成的 Mac mini 上跑一个 300 亿参数的本地模型，能不能给自家金融 App 写 Android UI 测试，哪怕只写其中最枯燥的那部分。不接云，不订订阅，就一台已有的机器和一个已经下载好的模型。短答案是"有时候"。长答案花了好几周，产出一份 198 页、自己跟自己打架的报告。

设备与模型

装置本身很具体：M4 Pro 的 Mac mini，48 GB 统一内存；Pixel 模拟器跑 Android 13（API 33）；Java 21、Maven，测试栈是 TestNG 7.11.0、Appium Java Client 10.0.0、Appium Server 3.0.2、UiAutomator2 5.0.4、Selenide 7.0.6，报告交给 Allure。模型侧是 Ollama 加 OpenCode 1.17.11，主模型 Qwen3-Coder-30B，混合专家，305 亿总参数、33 亿激活，量化到 Q4_K_M，约 18.5 GB。第二个是 278 亿的稠密模型，约 17 GB；文档把它写成 Qwen3.6 27B，这个名字没核实过。

图 1｜设备与模型清单，先看清实验装置

第一次尝试，是把它累垮了

第一次把整套活一次派下去：架构、Maven 工程、依赖版本、Appium 与模拟器配置、driver 生命周期、Page Object、测试、编译、端到端运行、Git，一个提示里全要。模型在 3.1 万到 3.3 万 token 附近忘了开头给的约束。编造依赖版本、用不兼容的 API，把 driver 生命周期写两遍，加了没人要的抽象，在该写测试的地方写了 assertTrue(true)，在任何东西通过之前就提交了代码。

由于一次请求里塞进了太多彼此耦合的任务，模型不是变蠢，是被塞垮的。于是把范围砍到一个 DriverManager、一个 BaseTest、一个冒烟测试。就在这里发生了没预料到的事：那个 278 亿的模型评审这一小片代码时抓到一个真实的 bug，AndroidDriver 从没通过 WebDriverRunner 注册到 Selenide，Selenide 其实什么都没在驱动。这个漏网之鱼此前没人看见。修掉之后冒烟测试第二次就过了。算不上胜利，但一个本以为没用的模型给出了真结果。

图 2｜一次登录烧掉 42 分钟和九万多 token

42 分钟，一次登录

完整场景通过 Appium MCP 跑：引导页、登录、关掉快速登录的底部弹层、在主界面翻一翻。只用一个 MCP server，不是一大群。耗时 42 分 24 秒，约 9.2 万 token。四十二分钟，为一次登录。

时序拆开看更枯燥，索性压缩着列：找到跳过引导的按钮约 8 秒，一次点击 15 到 16 秒，一次截图 7 到 14 秒，一次层级 dump 9 到 30 秒，找到登录框 17 到 18 秒，点元素 18 到 19 秒，输入一个值约 4 秒。有些查找能到 35 秒，查找失败一次约一分钟，收尾关停 38 秒。除此之外，模型反复索要本来就有的截图和层级、来回滑动、点坐标、按返回键、重新分析已经查过的状态。

慢本身不算错。慢叠加错才是问题：有一轮报告 BUILD SUCCESS，实际跑的是 LoginIT 而不是 LogoutIT。绿灯并没有确认真正要跑的那个测试。这更像验证设计的 bug，而不是模型的 bug，可它把"42 分钟"变成了"42 分钟且没有结果"。

图 3｜链上多处一起断，不只是模型不够聪明

失败来自不同层面

还有几类失败，性质各不相同。模型把 MASKED 这串字面文本输进登录框，因为它把规格里的脱敏策略当成了一个要输入的值。密码跑到了登录框里，因为调 set_value 时没带上密码框的 elementUUID。

用 touch_outside 关掉快速登录弹层一直不稳，直到换成系统的 Android 返回键。

多加上下文、再塞一个 agent 都解决不了这些，由于这些失败分属不同层面：数据策略、工具契约，以及一个不会安静下来的界面。

报告本身也是个问题。198 页，约 14800 词，由大概二十几份文档拼贴而成，没有封面、没有日期、没有作者，开头是一份报告的中段，结尾停在一个 YAML 块上。认证流程被描述了十五六遍，touch_outside 十三遍，MASKED 十六遍。结论还互相打架。一页说"没有创建出可用的 Android 测试框架"，另一页说"最小框架：可用。LoginIT：可用"，第三页说"代码生成：禁止"。没有一句是谎话，每一句都来自不同阶段、各有各的完成定义。第一句是大自治那次，第二句是最小切片，第三句出自 locators 还没建立之前。可读者分不清该信哪一句：翻开开头是失败，翻到中间是能用，翻到结尾是禁止。

教训很无聊，是踩坑换来的：每一条结论都标日期，只维护一张状态表，别把不同阶段的报告订成一个 PDF。否则，一次诚实的实验读起来会像一份自我推翻的宣传册。文档里原本带着内部名称、主机和测试数据，发表前全清掉了。

外部证据怎么说

人们最先引用的是 SWE-bench Verified。官方的 OpenHands 加 Qwen3-Coder-30B-A3B-Instruct 提交解出了 500 个实例里的 258 个，51.6%，pass@1，不给提示、不给测试知识。

这是真结果，不该一笔带过。可这个基准测的是 Python 仓库、简单的工具集、确定性的测试，没有模拟器、没有设备，也没有登陆界面。模型有一半时间能解对一道简短、隔离、可测试验证的 bug，另一半解不对。

自治工作里一半失败不可接受；对人会先读一遍的草稿，可能有用。这个基准告诉边界在哪，没告诉你模型擅长移动端测试。差一点就写成那样。

移动端的研究更薄，指向却一致。2023 年一篇 QRS 论文发现，ChatGPT 写出的 Appium 脚本语法正确，却用了不兼容或已废弃的 API，还处理不好输入焦点和弹窗。2024 年一项覆盖 9 个模型、115 个真实 App 的研究，用文本或 XML 时页面通过率约 71%，用截图时约 65%，缺陷发现接近 51%，而提升大多来自人去打磨输入。ScenGen 用五个分工不同的 agent 拿到结果，那是一套架构，不是一句"生成个测试"的提示词。

工具调用才是断掉的地方

Qwen3-Coder 常丢掉工具调用的开标签；另有报告说经 Ollama 的 qwen3-coder:30b 把工具调用当纯文本返回。即然一步出错会让后面全跟着错，二十步在每步 95% 可靠率下只剩约 36% 成功，90% 时只有 12%。

上下文也是一团乱。Ollama 按显存挑默认值：24 GiB 以下 4K，24 到 48 GiB 之间是 32K，48 及以上 256K。第一次跑是 32K，提到 128K 之后更稳，没更快，多余的动作还在。“分配了 128K"不等于"用好了 128K”，长上下文模型从输入中部检索的能力还会变差。

真正断掉的地方，是五层叠在一起：丢失的工具调用；一段满是动画和系统弹窗的长循环，早期错误一路传递；9.2 万 token 的日志和 XML，有用的那点可能藏在任意位置；每个动作 8 到 35 秒，“试一次、读结果、改"不再划算；再加上没有确定性的验证。最后那层最危险，因为 BUILD SUCCESS 会凭空制造信心。

分析里的三个错

复盘下来，有三个分析错误，而且是同一个毛病。把"一个文件、一个模板、自动检查就够了"当成结论写出来，读过的任何研究都不支持。一个文件里有三十次设备交互，比十个文件、每个一条命令加确定性结果更难。真正救你的是短的反馈回路，不是文件小。

第二个错，是写到"几十个 MCP 工具”。其实只有一个 server。一个看起来合理的细节比"不知道"更糟，因为它听着对，而且没人去核。

第三个错，是差点把 SWE-bench 的 51.6% 读成"适合移动端"。那个基准测的就是带测试的短 Python 任务，仅此而已。

一套收敛的配置长什么样

收敛出的配置小得多。模型是一个函数，不是 agent：输入一份 login_page.xml 快照，再加一个现成的 ProfilePage.java 当样式范例，输出一个 LoginPage.java。模型从不调用 Appium，不挑工具，不持有状态，从而把不确定的设备交互挡在外面。这套配置搭好后做了 dry run，全部主张就这些：一次预演，不是生产记录。

为什么是 32K 不是 128K？一页源码加一个例子轻松放得下，128K 是一次长 MCP 会话的体量，不是这个任务的。更多上下文不自动等于更好。

主要的保险是一个 locator 检查，模型不许自己编 id：

import re
def xml_ids(page_source):
    return set(re.findall(r'resource-id="([^"]+)"', page_source))
def java_ids(java):
    return set(re.findall(r'AppiumBy\.id\("([^"]+)"\)', java))
unknown = java_ids(java) - xml_ids(page_source)

unknown 非空就是错误，不是"差不多对"。错误回灌进提示词，最多试三次，然后过编译关卡：

这些检查抓得住语法、编造的 id 和编译问题，抓不住含义：错误的等待、错误的 API、一个匹配到两个元素的 locator。

还有些局限没有解决。iOS 上的 XCUITest 没有 resource-id，只有 name、label、value；没设 accessibility identifier 就只剩文本，而文本随语言变。屏幕外元素、系统告警、键盘、WebView、React Native 或 Flutter 的内容，常常根本不出现在快照里。

Android 上 Compose 常给出空的 resource-id，testTag 不开 testTagsAsResourceId 就不可见，合并语义还会藏起子元素。手势从 XML 里根本读不出来：是 click、longClick、swipe 还是 drag？模型默认 click()，能编译，但是错的。

import xml.etree.ElementTree as ET
root = ET.parse("login_page.xml").getroot()
for node in root.iter("node"):
    rid = node.get("resource-id")
    text = node.get("text")
    desc = node.get("content-desc")
    cls = node.get("class")
    if rid or text or desc:
        print(rid, text, desc, cls, node.get("bounds"))

iOS 上对 XCUIElementType* 用 name、label、value 做同样的事。元素不在快照里，工具就该说"不在快照里，滚动后重新 dump"，而不是编一个 id。解析器更快、更稳，而且不会幻觉。

分工可以按这个来布署：locator 由解析器或 Appium Inspector 出，绝不由模型出；Page Object 草稿的结构来自本地模型、locator 来自解析器，然后过 locator 检查和编译；失败分诊交给拿得到日志和页面源码的模型，人来拍板；自主设备控制交给云端模型或人。真正该盯的指标是从场景描述到被接受的可用测试的耗时，旁边并列编译次数、人工修正次数、假 BUILD SUCCESS 次数、真实界面上缺失的 locator 数。

还要有一条止损线，免得争论变成口味之争：拿十个真实界面，如果少于七个能走完"快照、生成、locator 检查、编译、冒烟，且最多人工修一次"就停。别加 agent，别加上下文，别重写提示词。停下来本身也是一个结果。

本地模型没有取代人。这个模型找到了一个此前漏掉的 bug，帮着写草稿，加速了一部分体力活；也为一次登录花了 42 分钟，对着错的测试打出了绿灯。两件事都成立。模型不是系统，系统才是那个检查输出的东西。在让模型碰测试之前，先问清楚什么能证明它做对了。答案是"人会看一眼"，那是草稿；是"编译并跑测试"，那是工程；是"模型自己会搞清楚"，那就是在为一次登录付 42 分钟和 9.2 万个 token。
